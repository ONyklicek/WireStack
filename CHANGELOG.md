# Changelog

All notable changes to the Wire ecosystem will be documented in this file.

## [1.6.2]

### Added
- **Field-level actions — `suffixAction()` / `prefixAction()` / `hintAction()`.** An input can now carry an interactive `Action` in its affix or hint area — a Filament-style lookup/generate/verify button — running server-side with the same reactive `$get` / `$set` / `$state` context as `afterStateUpdated()`: `TextInput::make('title')->suffixAction(Action::make('to_upper')->action(fn ($get, $set) => $set('title', strtoupper($get('title')))))`. The action's Closure cannot be serialised to the client, so the rendered button carries only the field's state path and the action name; on click the new `WireForms\Concerns\InteractsWithFieldActions::callFieldAction()` endpoint re-resolves the field from the live form definition, locates the action, and invokes its callback with the field accessors. Affix actions are owned in core by an extended `Foundation\Concerns\HasPrefixAndSuffix` (now holding prefix/suffix/hint `Action` slots plus `hasPrefixContent()`/`hasSuffixContent()`), behind the new `Foundation\Contracts\HasFieldActions` contract that `Field` implements; the dispatch trait is `use`d by both `WithForms` and `WithTable`, so field actions work in a standalone form **and** inside a table action modal (which exposes its form via `getActionModalFormInstance()`). Rendered through `wire-forms::partials.affix-action` and the hint area of `partials/field-wrapper-start.blade.php`. Covered by `TextInputTest`, `FieldActionsTest`, and `FieldActionsTableTest`.
- **`Button` interactive form field.** A first-class, design-system-styled button bound to a Closure — `Button::make('generate_slug')->label('Generate')->icon('heroicon-o-sparkles')->action(fn ($get, $set) => $set('slug', Str::slug($get('title'))))` — the supported alternative to hand-rolling a `<button>` inside an `Html` field (which renders raw markup and bypasses the palette). Presentation (label / icon / color / size / outlined) is delegated to an internal core `Action`, so a form button shares the exact styling and colour resolver as table and modal actions, and it dispatches through the same `callFieldAction()` path. `WireForms\Components\Button`, rendered by `wire-forms::components.button`; covered by `ButtonTest` and `FieldActionsTest`.
- **Reactive `$get` / `$set` accessors now reach layout components, not just fields.** A `visible()` / `hidden()` / `disabled()` Closure on a `Grid`, `Section` or `Fieldset` now receives the same live accessors a field does — `Section::make('Billing')->schema([...])->visible(fn ($get) => $get('type') === 'business')` — so a whole section can show/hide on a sibling's value. The accessor wiring was hoisted from the forms-only `InteractsWithFormState` into a canonical core owner, `Foundation\Concerns\InteractsWithState` (fields keep their own-value/`$state` semantics by overriding `resolveOwnState()`; layouts resolve sibling state against their resolved absolute path). `LayoutComponent` implements `HasStateAccessors` and binds the owning Livewire instance to itself inside `prepareChildren()` (covering top-level and nested layouts). Covered by `LayoutTest` and `ComponentTest`.
- **`describe-component-api` resolves display components by short name.** The wire-boost MCP tool (and `list-component-types`) could not resolve `html`, `placeholder`, `alert` or `view-field` — display components lived in a sub-directory with no registered base class, so `TypeCatalog` had no category for them and only an FQCN worked. A canonical `WireForms\Components\Display\Display` base class (which `Html` / `Alert` / `Placeholder` / `ViewField` now extend) plus a `displays` entry in `TypeCatalog::CATEGORIES` makes them discoverable by kebab short name like every other component type. Covered by `TypeCatalogTest`.
- **CI runs the behaviour suite against live MySQL, MariaDB and PostgreSQL.** All six test `TestCase`s now build the `testing` connection from environment variables (`DB_CONNECTION` + `DB_HOST`/`DB_PORT`/`DB_DATABASE`/`DB_USERNAME`/`DB_PASSWORD`), defaulting to in-memory SQLite so local runs and the main matrix are unchanged. A new `.github/workflows/database-tests.yml` spins up `mysql:8.0`, `mariadb:11` and `postgres:16` service containers and runs the result-based tests that execute real queries (search, filters, sorting, exports, CRUD via `TableQueryServiceTest` + the Feature/Standalone/Integration suites) against each server; the dialect-specific Unit suites that assert exact `toSql`/`toRawSql` strings stay on SQLite in the main workflow.

### Fixed
- **Wizard modals render their `modalFooterActions()`.** Footer actions added to a stepped action (`->steps([...])->modalFooterActions([...])`) were silently dropped — `getModalConfig()` carried them, but `wizard-footer.blade.php` never rendered them and `action-modal.blade.php` did not pass them into the wizard include, so the callback never fired and no error surfaced. The wizard footer now renders `before`/`after` footer actions alongside Back / Next / Submit, exactly like the non-wizard footer.
- **Column `filterOperator()` is honoured on the main table.** A `TextColumn::make('email')->filterable()->filterOperator('starts_with')` was silently ignored on the primary table: `TableQueryService::buildPlannerFilters()` hard-coded `operator: '='` for column-level filters, so `getFilterOperator()` (default `like`) only affected sub-row filtering. Column filters now route through the canonical `Column::applyFilter()` — the same owner sub-rows already use — so the configured `filterType` / `filterOperator` (partial `like` by default, `starts_with` / `ends_with` / comparison operators, relation `whereHas`) apply consistently on the main table. Covered by `TableQueryServiceTest` (default `like` partial match vs a `filterOperator('=')` exact match).
- **Repeater validation descends into nested layouts.** `Repeater::getItemValidationRules()` collected rules only from direct `Component` children, so fields wrapped in a `Grid`/`Section` inside a repeater — `Repeater::make()->schema([Grid::make()->schema([TextInput::make('name')->required()])])` — were never validated and invalid rows could be saved. Rule collection now recurses through `LayoutComponent` children. Covered by `RepeaterTest`.
- **`Form->disabled()` propagates into layout children and repeaters.** Only direct field components received the disabled state; fields inside a `Section`/`Grid`/`Repeater` in a disabled form stayed editable, and a repeater's add/remove/reorder buttons stayed active. `LayoutComponent::prepareChildren()` now takes a `disabled` flag, marks the layout, and cascades to descendants (`FormRuntime::prepare()` forwards `config->isDisabled`), so the repeater's own `isAddable()`/`isDeletable()`/`isReorderable()` — already gated on `isDisabled()` — turn off. Covered by `FormStandaloneTest` and `ComponentTest`.
- **Context-free dynamic action properties evaluate on record-less actions.** The `HasDynamicProperties` getters skipped their Closure whenever `$context` was falsy (`if ($callback && $context)`), so a `HeaderAction`/`BulkAction` — which carry no record — silently ignored a `->label(fn () => …)` / `->color(fn () => …)` and fell back to the default. A new `shouldInvokeDynamicCallback()` gate now runs zero-argument Closures even without a record, while a record-scoped `fn ($record) => …` still falls back (instead of erroring on a null record). Covered by `HeaderActionTest`.
- **Exports and the rendered table apply the default sort identically.** With a `defaultSort` configured, the export path (`getFilteredTableQuery()`) fell back to `getDefaultSort()` when no explicit sort was set, but the render/summary path (`buildTableQuery()`) passed `null` (no sort) — a latent asymmetry if the sort state was ever emptied while a default existed. `buildTableQuery()` now mirrors the `?: getDefaultSort()` fallback.
- **PostgreSQL search no longer interpolates the column into raw SQL.** `PostgresSearchStrategy` built its qualified-column clause with `orWhereRaw("{$column} ILIKE ?")`, inconsistent with `MySqlSearchStrategy` (safe `orWhere`) and with the `SqlSafety` gate `ApplySorting` uses. It now routes through the query builder — `orWhere($column, 'ilike', $term)` (the Postgres grammar supports `ilike`) — so the qualified column never reaches a raw string; the value stays bound as before. Not an exploitable hole (the column comes from Eloquent metadata) but it makes the safety convention uniform. Covered by `SearchStrategiesTest`.
- **Incomplete `BETWEEN` filter bounds no longer produce a match-nothing clause.** `ApplyFilters` passed `whereBetween($column, [$values[0] ?? null, $values[1] ?? null])`, so a single-sided range emitted `BETWEEN x AND NULL`, which matches nothing and silently returns no rows. A `BETWEEN` with only one bound now degrades to a `>=` / `<=` comparison and one with no bounds is skipped; a `NOT BETWEEN` requires both bounds (single-bound is ambiguous, so it is skipped). Not reachable through the shipped range filters (which already use `>=`/`<=`), so this is a hardening of the core query layer. Covered by `ApplyFiltersTest`.
- **`SelectFilter::searchable()` (and `native()`) actually change how the filter renders.** The flags were dead on the UI path: `tables/filters/select.blade.php` always emitted a browser-native `<select>` and the `Select` form field built by `getFormFields()` — the only place `->searchable()` was forwarded — is never rendered for a filter (that view path serves only the range filters). The same latent bug sat in the base forms `Select`: `components/select.blade.php` ignored `isSearchable()`/`isNative()` too, so the searchable combobox existed **only** in `BelongsToSelect`. The searchable Teleport + Floating UI combobox is now extracted to one canonical owner — `wire-core::partials.searchable-select` (single **and** multiple selection, `$wire.entangle`-bound, with an optional `$panelFooter` slot) — and consumed by the forms `Select` view (when `searchable() && ! native()`), the `BelongsToSelect` view, and the table `SelectFilter` view. `BelongsToSelect` previously carried its own near-identical copy of the combobox markup; it now delegates to the shared owner and contributes its "create new option" button through the panel-footer slot (`wire-forms::partials.belongs-to-create-option`), so the combobox UI lives in exactly one place. `SelectFilter::searchable()` now also opts the filter out of native rendering so `->searchable()` works on its own (an explicit later `->native()` still forces the native element). Covered by `SelectFilterTest` (native vs combobox render, multiple passthrough, `searchable()->native()` override), `SelectTest` (default native, searchable combobox, `native()` override), and `BelongsToSelectTest` (shared combobox render, native fallback, create-option footer).

### Changed
- **Wizard modal button labels are configurable and translatable.** The wizard `Back` / `Next` and the submit-in-progress `Saving…` labels were hard-coded `__('…')` calls in the default translation namespace with no fluent API. `HasModal` gains `modalPreviousActionLabel()` / `modalNextActionLabel()` / `modalSavingLabel()`, surfaced through `getModalConfig()`, each falling back to a new `wire-core::actions.{wizard_previous,wizard_next,submit_saving}` key (English + Czech shipped). The non-wizard footer's `Saving…` uses the same configurable label. Covered by `HasModalTest`.
- **Remaining hard-coded UI strings moved to translation keys.** The table's actions-column header fell back to a hard-coded Czech `'Akce'` (`tables/index.blade.php`) and `ExportAction::makeExport()` set a literal English `'Export'` label; both now resolve through `wire-table::messages.{actions_label,export_label}` (English + Czech), so every user-facing string in the runtime packages is translatable.
- **Reactive field-action recipes are documented for AI agents.** The bundled wire-forms guideline (`packages/boost/resources/boost/guidelines/wire-forms.blade.php`) documents `suffixAction()` / `prefixAction()` / `hintAction()`, the `Button` field, and the layout-level `$get`/`$set` accessors, so an agent reaches for a first-class field action instead of an `Html` field with a hand-wired `wire:click`. `DocsIndexTest` asserts the shipped corpus surfaces these recipes.


## [1.6.1]

### Added
- **Filament-style reactive state accessors in every field closure.** Dynamic field callbacks — `visible()`, `hidden()`, `disabled()`, `afterStateUpdated()` — now receive `$get`, `$set` and `$state` resolved against the **live** Livewire state bag, so a field can react to a sibling's value without reaching for a global `Livewire::current()` + `data_get()` workaround. The mechanism is a new canonical seam: `EvaluatesClosures::evaluate()` merges named accessors into the evaluated Closure when the component implements the new core contract `Foundation\Contracts\HasStateAccessors`, and `WireForms\Concerns\InteractsWithFormState` supplies them for fields. `$get('sibling')` reads another field under the same `statePath`; `$get()` reads the field's own value **live** (reflecting a `$set` made earlier in the same closure), while `$state` is a snapshot taken at call time; `$set('sibling', $value)` writes through the canonical `StateContainer::writeInto()` so it is StateContainer-safe and works identically inside a table action modal. Documented in the new `docs/forms/reactive-fields.md`.
- **`afterStateUpdated()` reactive hook with a single canonical owner.** A field can run a callback right after its bound value changes — `->afterStateUpdated(fn ($state, $old, $get, $set) => …)` — receiving the new value, the previous value, and the reactive accessors (parameters resolved by name, any subset in any order). Registering a callback **auto-enables `live()`** (without a server roundtrip the hook could never fire). The hook is owned in core by the `Foundation\Concerns\HasAfterStateUpdated` concern behind the `Foundation\Contracts\HasStateUpdatedCallback` contract; both form hosts route to it through one place — `WireForms\Concerns\DispatchesStateUpdates` maps the Livewire `updated` dot-path to the matching prepared field and fires its callback, so standalone `WithForms` components and table action modals share the lookup instead of each re-implementing it.
- **Modal footer actions.** Add extra buttons to an action modal's footer with `->modalFooterActions([ModalFooterAction::make('generate_slug')->action(fn ($data, $set) => …)])`. Each callback receives the live form-data bag as `$data`, a `$set` writer for it, `$component`, and the modal's `$record` / `$records` context, so a footer button can read and write the in-progress form without submitting it. `->submitsForm()` validates the form first, `->closesModal()` closes the modal after the callback returns, and `->position('before'|'after')` places the button around the built-in Cancel/Submit. Owned by `Core\Actions\ModalFooterAction` and the `Modals\Concerns\HasFooterActions` trait, rendered through `tables/partials/modal-footer-actions.blade.php`.

### Fixed
- **A form now propagates its Livewire instance to every field, not just the StateManager.** `Form::livewire()` forwarded the host only to the `StateManager`, leaving each `Field`'s `BelongsToComponent::getLivewire()` `null`, so `$component->getLivewire()` inside a `visible()` / `disabled()` closure returned `null` and reactive visibility could only be made to work through a `Livewire::current()` hack. `FormRuntime::prepare()` now forwards the resolved instance to every component — directly for top-level fields and recursively via `LayoutComponent::prepareChildren($parentPath, $live, $livewire)` for nested layouts — so fields resolve live state through the declared API. Combined with the accessors above, the `Livewire::current()` workaround is no longer needed.
- **`required()` on a hidden field no longer blocks submit.** `FormValidationResolver` flattened the schema and collected rules from **every** field regardless of `visible()`, so a `required()` rule on a field hidden by `->visible(fn ($get) => …)` failed validation against a value the user could never enter — the form refused to submit and `->action()` never ran. The resolver now skips components whose `isVisible()` is `false` when building rules, messages and attributes (visibility evaluated against live state, so a field toggled hidden by a sibling's value is excluded only while it stays hidden); repeaters are filtered the same way.
- **Multi-step wizard steps for a header action receive runtime context.** `getStepFormInstance($livewire, $context, $step)` passes `$context` into `ModalStep::getSchema($context)`, but for a `HeaderAction` the context was always `null` (header actions carry no record), so a `->schema(fn ($data) => …)` Closure that builds a later step from earlier answers could not resolve. `resolveCurrentModalAction()` and `resolveActionModalFormInstance()` now expose the live `modal.action.formData` bag as the header-action context, so a wizard's second step can branch on what was entered in the first. Covered by `WithTableWizardTest` ("passes the live form-data bag as context to a header wizard step", "builds the second step schema from first-step data").
- **Repeater add / remove / reorder no longer fatals with "Public method [addRepeaterItem] not found on component".** The Livewire action endpoints backing a `Repeater`'s buttons were not exposed on every host that can embed a form. They are now owned by one canonical trait, `WireForms\Concerns\InteractsWithRepeaters` (`addRepeaterItem` / `removeRepeaterItem` / `reorderRepeaterItems`), `use`d by both `WithForms` and `WithTable`, with writes routed through `StateContainer::writeInto()` so they work through the table's `tableState` StateContainer bag as well as plain array properties.

### Changed
- **`StateContainer::writeInto()` is the one writer for nested state.** Writing a value at a dot-path that crosses a `StateContainer` (the bag a table action modal binds) cannot go through `data_set()` — it silently drops the write on the overloaded `ArrayAccess` element. `writeInto()` walks the path, delegates to the container's `set()` / `replace()` when one sits on the path, and falls through to `data_set()` for plain hosts. `StateManager::set()`/`fill()`/`setState()`, the field `$set` accessor, and the repeater mutation endpoints all delegate to it, so the StateContainer-aware traversal lives in exactly one place.
- **Reactive-field behaviour is documented across the docs site and the AI guidelines.** New `docs/forms/reactive-fields.md` (accessors, conditional fields, `afterStateUpdated()`, prefilling a form from an action, footer actions); `docs/forms/overview.md` notes the live accessors on the inherited field API; `docs/core/modals.md` gains a "Building a step from earlier data" example showing `->schema(fn (array $data) => …)` (live even for header actions) and `docs/core/actions.md` cross-links it. The bundled wire-boost guidelines (`wire-core`, `wire-forms`) and the `wire-forms-development` skill document the `$get`/`$set` accessors, `afterStateUpdated()`, hidden-field validation skipping, `fillFormUsing()`, footer actions, and the dynamic wizard-step schema — so an AI agent stops reaching for `Livewire::current()`.

## [1.6.0]

### Added
- **New `nyoncode/wire-boost` package — AI tooling for the whole Wire ecosystem.** A `laravel/boost`-style companion that teaches AI agents the wireStack API surface and lets them introspect a running app. It ships an MCP server (built on `laravel/mcp`) exposing **20 tools** — including wireStack-specific introspection (`ListWireComponents`, `ListComponentTypes`, `DescribeComponentApi`, `DescribeForm`, `DescribeTable`, `DescribeInfolist`, `ListIcons`, `SearchDocs`, `WireConfig`) alongside general app tools (`ApplicationInfo`, `DatabaseSchema`/`DatabaseQuery`/`DatabaseConnections`, `ListRoutes`, `ListArtisanCommands`, `Tinker`, `ReadLogEntries`, `LastError`, `BrowserLogs`, `GetAbsoluteUrl`) — plus bundled AI guidelines (`wire-core`/`wire-forms`/`wire-table`/`wire-sortable`) and agent skills per package. An `InstallCommand` wires the MCP server and guidelines into the host app, and the tool set degrades gracefully when optional packages (`wire-forms`/`wire-table`/`wire-sortable`) are absent. Like `wire-sortable`, the package is excluded from `composer analyse`.

### Fixed
- **`TernaryFilter` actually filters again.** Selecting "Yes"/"No" returned **zero rows** for every boolean column. `TernaryFilter` carried correct boolean-coercion logic in its `apply()` (mapping the rendered `<select>` strings `'true'`/`'false'` to a real boolean `where`, plus a `= false OR IS NULL` branch under `nullable()`), but never overrode `bypassesPlanner()` (inherited `false`), so `TableQueryService` routed it through the `QueryPlanner` as a plain `FilterDefinition('active', '=', 'true')`. The resulting `where active = 'true'` matches nothing against a 0/1 boolean column — `apply()` was dead code on the UI path. `TernaryFilter::bypassesPlanner()` now returns `true` (same opt-out `DateFilter` uses for its non-planner-expressible month mode), routing ternary state through `apply()` so the string→boolean coercion and the nullable `OR IS NULL` expansion run. Covered end to end by `TernaryFilterApplyTest` (truthy / falsy / `nullable()` NULL-as-false / inactive).
- **`BarChartWidget` bars render with their colour in consuming apps.** The bar fill (`from-*-500 to-*-600`) and accent text (`text-*-600 dark:text-*-400`) are chosen at runtime by the canonical `HasColor::getGradientFillClasses()` / `getFillTextClasses()` resolvers, whose literal class strings live only in package **`src/`**. A consumer's Tailwind build scans the package **views** (`resources/views/**/*.blade.php`) but not `src/` (per `docs/getting-started.md`), and Tailwind v4's project auto-scan stops at the gitignored `vendor/`, so those gradient/text utilities were never emitted into the host CSS — bars rendered with the correct width/height (`w-[var(--value)]` / `h-[var(--value)]`, which *are* literal in the partials) but **no visible colour**. A scanner-only safelist view (`resources/views/widgets/bar-chart/safelist.blade.php`, hidden and never `@include`-d) now lists every gradient-fill / accent-text class the widget can emit plus `bg-gradient-to-r` / `bg-gradient-to-t` and the value-driven sizing utilities, so a host scanning the package views generates them without any manual `tailwind.config.js` safelist. `HasColor` stays the canonical runtime owner; the safelist only guarantees static discoverability and is kept in sync by `BarChartSafelistTest`. The monorepo workbench masked the bug because its `app.css` also scans `packages/*/src`.
- **wire-boost AI guidelines and skills no longer ship example code that fails to run.** A code-grounded audit of the bundled guidelines (`packages/boost/resources/boost/guidelines/*.blade.php`) and agent skills (`packages/boost/resources/boost/skills/*/SKILL.md`) against the actual package source found six concrete examples an agent would copy verbatim and ship broken: `BadgeColumn::make(…)->color(fn ($state) => …)` (×2 — `Column::color()` takes `string|Color|null`, never a Closure; per-row badge colour is `->colorUsing()`); `->summarize(SummaryType::sum())` (no such static — `SummaryType` is a string-backed enum, so `SummaryType::Sum`); `EditAction::make()->modal(fn () => Modal::make()…)` (`HasModal::modal()` takes a `ModalContract` instance, not a Closure — `->modal(Modal::make()…)`); `Grid::make(2)` (the argument is the component name, not a column count — `Grid::make()->columns(2)`); and `Stat::make('Users', User::count())` (the `$value` parameter is typed `string`, so `(string) User::count()` under `strict_types`). The dynamic side of wire-boost (the reflection-based MCP tools, config keys and icon lookups) was verified accurate and unchanged.

### Changed
- **wire-boost guidelines spell out *when* to use each colour/icon setter, not just that it exists.** Reflecting a real divergence in the wireStack API surfaced by the audit above: on `BadgeColumn`/`IconColumn`, colour resolves four ways by intent — `->color('success')` (one fixed colour, `string|Color|null`), `->colors([state => color])` (static map), `->colorUsing(fn ($state) => …)` (computed per row), or nothing when the state is an enum implementing `HasColor` (auto-resolved); icons mirror this (`->icon()` / `->icons()` / `->iconUsing()` / enum `HasIcon`). On **actions**, by contrast, `->label()` / `->icon()` / `->color()` / `->tooltip()` / `->size()` each accept `string|Closure|null` directly (the Closure receives the record, `fn (Model $record)`), so dynamic values do **not** go through a `*Using()` variant. The guidelines now document both rules side by side so an agent does not cross-apply one surface's convention to the other, plus that `->action(fn ($record) => …)` receives the current record.

## [1.5.3]

### Added
- **Multi-step wizard modals render end to end.** `HasModal::steps([ModalStep::make()…])` previously only stored the steps and set `hasModal = true` but never built a form instance, so an action with steps fell through to the empty/confirmation branch — `action-modal.blade.php` rendered only `$actionFormInstance` / `$actionInfolistInstance`, with no step renderer, indicator, or navigation. The wizard now has a full runtime: each step's schema is built as a `Form` sharing the single `modal.action.formData` state bag (data persists across steps); the modal renders a step indicator plus Back / Next / Submit driven by `modal.action.currentStep`; `nextActionModalStep()` validates the current step (field schema via the Form runtime, then `ModalStep::validation()` rules, then the `afterValidation` hook) before advancing and runs the next step's `before` hook to pre-fill it; `prevActionModalStep()` steps back without validating; and `submitActionModal()` re-validates every step cumulatively before executing (the per-step `afterValidation` hooks are skipped on submit so they don't fire twice). `HasModal::getStepFormInstance()` / `getModalStep()` / `getStepCount()` own per-step form building, and `hasFormModal()` / `hasFormInstance()` / `doesRequireConfirmation()` now account for multi-step actions.
- **`Action::modal(ModalContract)` configures an action from a declarative modal object.** The `Modals\{Modal, SlideOver, ConfirmationDialog, Wizard}` config objects shipped with full fluent APIs and tests but were wired to nothing — no action consumed them, and the only rendered path was the action-fluent API (`requiresConfirmation()` / `slideOver()` / `steps()`). They are now first-class inputs: `->modal(Wizard::make()->steps([…]))`, `->modal(SlideOver::make()->heading(…))`, `->modal(ConfirmationDialog::delete('User'))`, and `->modal(Modal::make()…)` translate the config object into the action's modal state and render through the existing runtime (a `Wizard` flows into the multi-step runtime above). `ModalContract` is enriched with the common getters every implementation already had — `getIcon` / `getIconColor` / `getColor` / `getSubmitLabel` / `getCancelLabel` / `hasStickyFooter` / `hasStickyHeader` / `getMaxHeight` / `getId`. (The `Modals\View\{Modal, SlideOver, Confirmation}Component` Blade components are unaffected — they remain the registered `<x-wire-modals::*>` rendering primitives.)

### Fixed
- **Teleported dropdown panels stay pinned across Livewire morphs.** A Livewire re-render can detach/replace a dropdown trigger or strip the inline `left` / `top` styles Floating UI writes (they are absent from the server HTML), so the panel recomputed its position against a disconnected node and collapsed into the **top-left corner** until the next scroll/resize. The dropdown bundle now guards `reposition()` with an `isConnected` check (positioning is skipped until both the reference and floating ends are reconnected) and re-pins via a `MutationObserver` on every morph that touches the panel, ignoring its own inline-style writes to avoid an update loop. Ships in the precompiled `wire-core-dropdown.js`.

### Changed
- **`SqlSafety` is now the wired canonical owner of SQL keyword / identifier safety.** It was documented as the mandatory gate for "anything touching SQL identifiers" but had **zero call sites**, while the actual safety was re-encoded inline. `SqlSafety` gains `normalizeDirection()` and `normalizeNullsPosition()`, and `SortClause` delegates to them — its duplicated `asc`/`desc` and `FIRST`/`LAST` allow-lists are removed. The two raw-SQL query pipes now route through it: `ApplyFilters` calls `assertValidOperator()` before interpolating an operator into a `whereRaw` sql-expression filter (the operator allow-list was documented but never enforced), and `ApplySorting` calls `assertValidQualifiedColumn()` before interpolating a column into a `NULLS` `orderByRaw`. This was not an exploitable hole — user input already flows through the query builder (quoted identifiers, bound values) and the raw paths use developer-provided expressions — but it makes the documented invariant true and removes the duplicate allow-list.
- **Button sizing has one canonical resolver.** The `xs/sm/md/lg` button padding scale (and its icon-only square-padding variant) was copy-pasted verbatim across `BaseAction::resolveButtonSizeClasses()`, `ActionGroup::getTriggerClasses()`, and `ButtonColumn::getButtonClasses()`; all three now delegate to the new `HasSize::getButtonSizeClasses($size, $iconOnly)` (next to `getBadgeSizeClasses`).
- **The confirmation modal's submit button delegates to the canonical colour owner.** `ConfirmationComponent::submitButtonClasses()` re-implemented its own hue `match` that had drifted from `HasColor::getModalSubmitButtonClasses()` (different hover hue, missing `active:` state); it now calls the canonical resolver, so the confirmation footer matches the table action-modal footers.
- **Column responsive visibility is owned by the `HasResponsive` trait.** `Column` carried an inline copy of `visibleFrom` / `hiddenFrom` / `getResponsiveClasses` / `hasResponsiveVisibility` that was byte-for-byte identical to the `HasResponsive` trait — which had no consumers. `Column` now `use`s the trait (its single canonical owner) and the inline copy is removed; the trait absorbs the previously Column-only `2xl` hidden breakpoint and `hasResponsiveVisibility()`.
- **Dead table concerns removed.** `Concerns\HasFormatting` (standalone static money/number/date formatters, superseded by `Column::formatStateUsing()` and column-local helpers like `TextInputColumn::money()`) and `Concerns\WithRowPolling` (a self-described legacy shim whose real `refreshRow()` lives on `WithTable`) had no production consumers and are deleted.

## [1.5.2]

### Fixed
- **Header-action form modals seed their `fillFormUsing` defaults.** `HasModal::getFormDefaults()` and the fill step in `getFormInstance()` were both gated on `$context !== null` — a guard meant to avoid calling a record-typed row-action closure with `null`. ## [1.5.0]

### Added
- **Enum-sourced options auto-add an `in:` validation rule.** When a single-value `Select` or `Radio` takes its options from an enum class, the field is automatically constrained to those keys (`Rule::in([...])`) — a tampered or stale submission outside the enum is rejected without the owner restating the rule. The logic lives on `WireForms\Concerns\HasOptions` behind the new `WireForms\Contracts\ProvidesImplicitValidationRules`, and `HasFormValidation` merges it in. It is skipped when options are a plain array (the set may be dynamic), for multi-value fields (array state can't be a single `in:`), and when the owner already declared an `in:` / `Rule::in()` / `Rule::enum()` rule.
- **`TextInput::datalist()` accepts an enum class.** Passing an enum class uses its case labels as the input's suggestion list, mirroring the option-field shorthand.
- **Enum classes can populate field options directly (Filament-style).** Any option-based surface now accepts a backed/unit enum class-string instead of a `[value => label]` array — `->options(Status::class)` — and expands it to a map keyed by the backing value (or case name for unit enums). Enums implementing `Foundation\Contracts\Enum\HasLabel` render `getLabel()` as the option label; enums exposing a `label()` method use that; everything else falls back to a headline of the case name. The expansion is owned by a single canonical method, `EnumResolver::options()` (plus `isEnumClass()` and the pass-through `normalizeOptions()`), and every surface delegates to it: form `Select`, `Radio`, and `CheckboxList` (via the new shared `WireForms\Concerns\HasOptions` trait), table `SelectColumn`, and table `SelectFilter` (whose former package-local enum `match` map is removed in favour of the shared owner). The generic column-level APIs accept it too — `Column::editable(type: 'select', options: Status::class)`, `Column::filterable(type: 'select', options: Status::class)`, and `Column::filterAsSelect(Status::class)`. Closures returning an enum class are expanded too; arrays pass through untouched.

### Changed
- **A label-less enum now displays a headline of its case name everywhere, not its backing value.** `EnumResolver::label()` (and therefore every display surface — table columns, infolist entries, exports, grouping, filter chips) previously fell back to the raw scalar for an enum that does not implement `Enum\HasLabel` (`Status::Active = 'active'` rendered `active`). It now resolves through the same canonical order as option labels — `HasLabel::getLabel()`, then a `label()` method, then `Str::headline($case->name)` (`Active`, `InReview` → `In Review`) — so the same enum reads identically on a cell, an export, and a `<select>` option. Enums implementing `HasLabel` and non-enum values are unaffected; `scalar()` (used for keys, copy values, comparisons, serialization) still returns the backing value.

### Fixed
- **`Action::visible(Closure)` is honoured again.** The Actions `HasVisibility` trait implemented `visible()` as `hidden(! $visible)`; for a closure, `! $closure` coerced the object to `true`, so the callback was discarded and `hidden(false)` made the action **always visible** — silently bypassing per-record visibility logic such as `->visible(fn ($record) => $record->canEdit())`. The trait now branches on the closure and stores a negating wrapper, matching the Foundation `HasVisibility` behaviour.
- **Repeater state path keeps its form prefix.** A `Repeater` nested in a form (or any layout) never had its own state path set during `prepareChildren()`, so `getStatePath()` dropped the prefix (returned `contacts` instead of `data.contacts`) and the add/remove handlers and `wire:model` bindings wrote to the wrong location. `LayoutComponent` now records a resolved absolute path during preparation (idempotent — re-running never double-applies the prefix) and `Repeater::getStatePath()` reads it.
- **Repeater items are validated at the correct paths.** Repeater child fields were flattened and validated at the template path (`data.label`) instead of the per-item path, so per-item rules never matched real data, and the repeater's own `min/max-items` / `array` rules were never collected (the resolver called `getValidationRules()` while `Repeater` defined `getRules()`). The validation resolver now treats repeaters as opaque during flattening and emits container rules at the repeater path plus per-item **wildcard** rules (`data.contacts.*.label`); `required()` on a repeater adds `required` + `array`.
- **`<x-wire-actions::button>` no longer fatals for header/bulk actions.** The component's fallback (taken when an action has no `getRenderData()`, i.e. `HeaderAction` / `BulkAction`) called the `protected` `resolveSolidColorClasses()` / `resolveButtonSizeClasses()` with missing arguments, throwing `ArgumentCountError`. The fallback now uses a single public `BaseAction::getButtonClasses()` that assembles base + size + color via the canonical resolver.
- **Relation (dotted) filter names work from the UI.** A filter named `customer.status` is bound nested by `wire:model` (`filters.customer.status.value`) but was read back with a flat key, so the value never applied and the chip's remove button couldn't find it. Filter init, the query service, indicator chips, sub-row filters, and `removeTableFilter()` now read/write through `data_get` / `Arr::set` / `Arr::forget` (pruning empty parent nests), so dotted names round-trip end to end.
- **Multi-value field state is typed as an array.** `Select` (multiple) and `CheckboxList` inherited `getStateType() === 'string'`, so a stray scalar was left as a string the bound control couldn't use. Both now report `'array'` (Select only when `->multiple()`), matching `Tags` / `KeyValue` / `FileUpload`.
- **`DateTimePicker` stores a serializable date string, not a Carbon.** The field hydrated its state to a `Carbon` instance inside the Livewire array, which is fragile to serialize and unparseable by the Alpine/native picker. A new format-qualified hydrator type (`date:<format>`) parses any date-like input and returns a mode-appropriate **string** (`Y-m-d`, `Y-m`, `H:i[:s]`, `Y-m-d\TH:i[:s]`); the core `StateHydrator` owns the generic formatting while the field owns its format.
- **Column text filters ignore non-scalar values.** `applyTextFilter()` built `"%$value%"` without a type guard, so a crafted/stale array column-filter value raised an "Array to string conversion" warning and a garbage `LIKE`. Non-scalar values are now ignored.
- **Cleared range filters no longer count as active.** The toolbar derived active filters with a bare `array_filter($tableFilters)`, so a range filter typed then emptied (`['min' => '', 'max' => '']` — a truthy array) stayed "active", contradicting the (correctly empty) indicator chips. The active check now recurses and rejects all-empty values.
- **`Toggle` colours and icons render.** `onColor` / `offColor` / `onIcon` / `offIcon` were fully wired in PHP but the view hardcoded `bg-primary-600` / `bg-gray-200` and drew no icons. The toggle now resolves its track colours via `getOnColorClasses()` / `getOffColorClasses()` (purge-safe, toggle-specific) and renders the on/off icons.
- **Sortable column reordering supports all columns and non-integer user keys.** Non-sortable column `<th>`s emitted no `data-column`, so they couldn't be drag-reordered and were silently dropped from the saved order; every column header now carries `data-column`. The per-user column-order persistence typed the user id as `?int`, throwing on UUID/ULID auth keys — the model, concern, and migration now accept `int|string` (migration column type configurable via `wire-sortable.user_key_type`: `id` / `uuid` / `ulid`).
- **`SortableTable::alwaysReorderable()` actually enables reordering.** The method was missing on the subclass and fell through to a `Table::macro` writing a different property, so `isReorderable()` stayed `false` and reorder mode never engaged. It is now a real method (implying `reorderable()`), and `getOrderColumn()` reads the `wire-sortable.order_column` config default that was previously ignored.

### Changed
- **Bulk-action buttons delegate to the canonical colour owner.** `actions/bulk-button.blade.php` re-encoded the palette with an inline `match` map whose outlined branch only handled `primary` / `danger` (rendering `success` / `warning` / `info` grey); it now calls `getButtonClasses()`, so every hue and the solid/outlined split come from the shared `HasColor` resolver.

##[1.2.0]

### Added
- **Poll change detection** – `Table::pollChangeDetection()` skips the full poll re-render (query + summaries + DOM morph) when a cheap checksum of the filtered data (`COUNT(*)` + `MAX(updated_at)` in one query) is unchanged since the last poll. Pass a closure (`->pollChangeDetection(fn ($query) => …)`) when parent timestamps don't capture relevant changes (e.g. child-table rollups). Opt-in; default behavior is unchanged.

The enum owns the per-type semantics (default labels, count formatting, SQL portability, empty-set results). Strings stay accepted and are normalized to the enum; unknown type strings now throw an `InvalidArgumentException` instead of silently rendering an empty footer value.

### Changed
- **Rollup grand totals compute in SQL.** Summarizing a rollup column (`->sums()` + `->summarizeSum()`) previously loaded every filtered parent row into memory and summed floats in PHP; the rollup alias is now aggregated in SQL over a derived table — no row loading, database decimal precision.

### Performance
- **Row selection is client-side — a checkbox click no longer costs a server roundtrip.** Selection state lives in Alpine, entangled (deferred) with `tableState.selection.records`: checkboxes, the select-all header state, row highlight, and the selection bar (count, plural label, deselect) all react instantly without re-rendering the table. The server state syncs with the next request (bulk actions always see the current selection); tables with a summary footer auto-commit selection changes debounced (~350 ms) so selection-scope totals and the scope toggle stay correct. Server methods (`toggleRecordSelection()`, `selectAllRecords()`, …) remain for backwards compatibility.
- **`subRowsLimit()` no longer loads full child sets into memory.** The eager load now fetches only `limit` rows per parent (native per-parent eager-load limit, window function) plus one `loadCount` query for exact "show more" totals; parents flagged show-all still load their full set. Previously every expanded/flattened parent loaded *all* children just so the limit could be applied in memory. On Laravel 10 (no per-parent eager-load limit) the loader transparently falls back to the previous full-load + in-memory limit, so behaviour is identical there.
- **Footer summaries batch into a single SQL query.** Every `query`-scoped summary previously ran its own aggregate query on each Livewire render (a footer with 5 summaries = 5+ queries per interaction). All SQL-native summaries now compute in one aggregate query (plus one for rollup columns over the derived table); sub-row grand totals batch the same way over the child query. Closure summaries, statistical types (median, stddev, …), and `when()`-restricted summaries keep the per-summary fallback with identical results.
- **Package views no longer go through the deprecated magic properties.** `index.blade.php` and the sub-row partials read `$component->tableState` directly (precomputed once per render) instead of `$component->tableFilters` & co., which rebuilt the legacy property map on every access — per row, per column. The map itself is now memoized, so user code on the legacy properties is cheaper too.
- **Row loops reuse the precomputed visible-column set.** Header, filter row, body cells, and sub-row tables no longer re-evaluate `canView()` (which may hit the Gate) and `isColumnVisible()` per cell — visibility resolves once per render (once per parent for sub-rows).
- **Selected records are memoized per request** (selection-scope summaries, grand totals, and bulk modals previously each ran the same query) and **group subtotals partition the page once** instead of re-filtering all page records per group.
- **`StateContainer::get()` traverses the path once** instead of the previous `has()` + `resolve()` double walk — it runs hundreds of times per table render.
- Capability auto-resolution in `TableQueryService` is skipped when the metadata registry holds no column/accessor metadata — removes a no-op per-column walk from every query build.

### Fixed
- **Query cache no longer serves page 1 for every page.** Pagination is applied inside the cache callback, so the page number was missing from the cache key (`cacheQuery()`) — all pages shared one entry for the TTL. The current page (or cursor) is now part of the key, including with a custom `cacheQuery(key: …)`.
- **`subRowsLimit()` on Laravel 10 showed too few children.** The per-parent eager-load limit (a window function) only exists on Laravel 11+; on Laravel 10 it applied a single global `LIMIT` across all parents, so the first parent received fewer than `limit` rows. The loader now detects the framework capability and falls back to full-load + in-memory limiting on Laravel 10.

Fields now default to deferred `wire:model` (values are sent with the submit call), eliminating both the text loss and the per-keystroke server roundtrip + table re-render. - **Rollup columns export their values.** Exporters resolved cell values only by column name, so a rollup column named differently from its aggregate attribute (e.g. `items_total` vs `items_sum_line_total`) exported empty cells; exporters now read the computed aggregate attribute.

### Migration Guide

1. Update `composer.json`:
   ```bash
   composer require nyoncode/wire-table:^0.1
   ```
   This will automatically install `wire-core` and `wire-forms`.

2. Find and replace namespaces in your codebase using the table above. Most common replacements:
   ```
   NyonCode\WireTable\Actions\ → NyonCode\WireCore\Actions\
   NyonCode\WireTable\Forms\Fields\ → NyonCode\WireForms\Components\
   NyonCode\WireTable\Notifications\ → NyonCode\WireCore\Notifications\
   ```

3. Layout components moved to sub-namespace:
   ```
   NyonCode\WireForms\Components\Layout\Section
   NyonCode\WireForms\Components\Layout\Grid
   NyonCode\WireForms\Components\Layout\Fieldset
   ```

4. Display components moved to sub-namespace:
   ```
   NyonCode\WireForms\Components\Display\Alert
   NyonCode\WireForms\Components\Display\Html
   NyonCode\WireForms\Components\Display\Placeholder
   NyonCode\WireForms\Components\Display\ViewField
   ```

5. DatePicker/TimePicker unified into `DateTimePicker`:
   ```php
   // Before:
   DatePicker::make('birth_date')
   TimePicker::make('start_time')

   // After:
   DateTimePicker::make('birth_date')->asDate()
   DateTimePicker::make('start_time')->asTime()
   ```

6. Blade render syntax changed:
   ```blade
   {{-- Before --}}
   {!! $this->getTable() !!}

   {{-- After --}}
   {{ $this->table }}
   ```

7. If you customized notification driver config, update class references to `NyonCode\WireCore\Notifications\Drivers\*`.
