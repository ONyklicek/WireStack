# Changelog

All notable changes to the Wire ecosystem will be documented in this file.

## [1.10.2]

### Changed
- **Per-column header filters are now a placement of the canonical `Filter`, not a second filtering engine.** The header-filter machinery had grown into a parallel mini-API baked into `Column`: a `$filterType` string discriminator with **two** `match` maps (`applyFilterCondition()` for SQL + `renderFilter()` for the view), ~14 ad-hoc `$filter*` properties, and duplicated apply logic (`applyBooleanFilter` / `applyDateRangeFilter` / `applyNumberRangeFilter`) that re-implemented what `TernaryFilter` / `DateFilter` / `NumberRangeFilter` already did — a textbook violation of the repo's "one canonical owner per behavior / no parallel `match` maps" invariant. A column filter is now a **placement** of a canonical `Filter` in the header cell: `Column` holds a single `?Filter`, and `filterAsSelect()` / `filterAsMultiSelect()` / `filterAsDate()` / `filterAsDateRange()` / `filterAsNumberRange()` / `filterAsBoolean()` (plus `filterOperator()` / `filterSearchable()` / `filterPlaceholder()` / `filterDebounce()` / `filterUsing()`) become **thin, 100%-BC factories** over `TextFilter` / `SelectFilter` / `DateFilter` / `NumberRangeFilter` / `TernaryFilter` — the column owns *where* it renders and *which attribute* it targets, the `Filter` owns *how* it applies / renders / indicates / persists. The ~360-line duplicated engine (property bag + both `match` maps + the four `apply*` methods) is **deleted** from the hot `Column.php`; relation wrapping now has one owner (`Filter::applyToColumn()`); and the 7 inline header partials stay as a distinct UI surface but are repointed from `$column->getFilterX()` to `$filter->getX()` (view selection is polymorphic via `Filter::inlineView()`). Column filters are now **planned through the same `QueryPlanner`** as panel filters — each `Filter::toPlannerDefinitions()` emits a `FilterDefinition` (text → `LIKE` / comparison, select → `=`, multi-select → `IN`, number-range → `BETWEEN` with one-sided degradation), so join handling + column qualification are shared; the two types the planner can't express as one clause (date `whereDate`, boolean `= false OR IS NULL`) transparently fall back to the shared `Filter::apply()` via the existing `bypassesPlanner()` seam. **No public API is removed** — every `filterAs*` signature and behavior is preserved (header state still lives under `columnFilters.<name>`); a new `Column::filter(Filter)` / `getFilter()` is the canonical entry point for attaching a ready-made filter. Because header filters are now real `Filter` objects, they inherit for free: **authorization** (`->can()` / `->visible()` gate both render and apply), **indicator chips** (`getActiveColumnFilterIndicators()` / `removeColumnFilter()` render removable chips alongside panel-filter chips, sharing the new `filter-chip` partial), and **query-string persistence** (`Table::queryString()` tracks/seeds column filters under a `col_<column>` URL parameter — ranges use `col_<column>_min` / `_max`; dotted relation names are skipped as with panel filters). A new **`TextFilter`** (operator-aware substring/`LIKE` filter) is the engine behind `->filterable()` text filters and is also usable as a standalone panel filter. Covered by new `ColumnCanonicalFilterTest`, `CanonicalFilterPrimitivesTest`, `FilterInternalsCoverageTest`, extended `WithTableFilterIndicatorsTest` / `WithTableQueryStringTest`, and migrated `ColumnFilterCoverageTest` / `ColumnTest` — all four package suites green (table 1008 passing), PHPStan clean, and **every `packages/table/src/Filters/*` file at 100% line coverage**. Documented in [`docs/table/filters/column-level.md`](docs/table/filters/column-level.md), the new [`docs/table/filters/text.md`](docs/table/filters/text.md), [`docs/table/filters/index.md`](docs/table/filters/index.md) and [`docs/table/columns/editing.md`](docs/table/columns/editing.md) (EN + CS), the wire-boost guidelines, and an implementation plan under `architecture/plans/column-filter-canonical-unification.md`.

### Fixed
- **`FileUpload` uploads no longer get collapsed to a dead temp path when they pass through the table state container.** Root cause: `StateSerializer::serializeValue()` (used by `TableStateSynthesizer` to dehydrate the `StateContainer`) stringified any `Stringable` value — and `Illuminate\Http\UploadedFile` / Livewire's `TemporaryUploadedFile` are `Stringable` via `SplFileInfo::__toString()` (which returns the pathname). So a file living in action-modal form state (`modal.action.formData.*`) was cast to its raw `/tmp/phpXXX` path **before** Livewire's own file-upload dehydration ran, and Livewire's file synth never saw it — the upload was lost and a dead path persisted. `StateSerializer` now hands any `SplFileInfo` (file-upload object) straight through untouched so Livewire's `$dehydrateChild` handles it. Covered by a new `StateEngineTest` case (a file object is returned as-is, even nested deep in the state tree).
- **`FileUpload` no longer persists (or renders) a leaked raw upload path as if it were a stored file (defense-in-depth).** Even when a `FileUpload` value still reaches the save step as a bare **absolute** filesystem path — e.g. a raw PHP `$_FILES` tmp_name like `/tmp/phpA1B2C3` — `SaveHandler::storeFieldFiles()` used to treat any non-`UploadedFile` string as an already-stored path and write it straight to the model, so the DB ended up holding a dead temp path (the file is deleted at the end of its upload request). `FileUpload` now owns one canonical classifier, `isStoredReference()` — a legitimate stored value is a disk-relative path or a full URL, **never** an absolute filesystem path — used by `SaveHandler` (a leaked absolute path is now **rescued** onto the configured disk via the new `FileUpload::storeFileFromPath()` when the file still exists, or **dropped** when it is gone, instead of persisting the raw path), and by `FileUpload::getStoredFiles()` / `getFilePreviews()` (a leaked absolute path is never rendered as a stored file). Legitimate relative paths and URLs pass through unchanged. Covered by new `SaveHandlerTest` cases (gone temp path → null; existing path → rescued to a disk-relative path; multiple field filters the dead entry but keeps real paths) and `FieldTypesTest` cases (`isStoredReference` / `storeFileFromPath` / `getStoredFiles` / `getFilePreviews`).
- **Stacked modals: polished layering, a canonical z-index owner, and a depth cap (follow-up to the 1.10.1 stacking).** The z-index scale and safety cap now have one canonical owner — `Modals\ModalStack` (`BASE_Z_INDEX` / `Z_INDEX_STEP` / `MAX_DEPTH`, `zIndexForDepth()`) — instead of `50 + depth*10` hard-coded in Blade. Suspended parent shells now paint **no** backdrop of their own — the active modal draws a **single** full-viewport scrim — so stacking N levels no longer compounds into a near-black overlay; each suspended shell is `inert` + `aria-hidden` so keyboard and assistive tech skip it entirely; deeper parents progressively scale/lift for a "stacked-cards" depth cue; and opening is capped at `ModalStack::MAX_DEPTH` levels to bound pathological re-entrancy. Covered by a new `ModalStackTest` (z-index owner) plus `ModalStackingTest` / `ModalComponentRenderTest` cases (single scrim, inert shell, depth-cue transform, three-levels-deep pop-back, and the max-depth guard), and re-verified in a real browser via the `table-modal-nested` driver (single scrim, elevated z-index, `Escape` pops only the top).

## [1.10.1]

### Fixed
- **Opening an action from within an open modal no longer destroys the parent modal — modals now stack.** The action runtime was built around a **single** open modal at a time (one `mountedAction` bag in the standalone `WithActions` host, one `modal.action.*` slot in the table's `StateContainer`), so opening an action while a modal was already open **clobbered** the parent: its form state was silently discarded and it could never be returned to. Opening an action now **stacks** the new modal on top instead: the parent stays open, dimmed behind the new one, and closing the top modal (`Escape` / close button / backdrop / a footer action that closes) pops just that level and **resumes the parent with its form data intact** — the last close clears the stack. There is **no new public API**: any callback that receives the host `$component` (a `ModalFooterAction`, a field action, an infolist action) can call `$component->mountAction(...)` (standalone) or `$component->openActionModal(...)` / `openBulkActionModal()` / `openHeaderActionModal()` (table) and it just stacks; a footer action that opens a nested modal is **not** auto-closed afterwards (a depth guard skips the close when the callback pushed a level). Implemented as a **suspend-stack** that leaves the existing single active-slot machinery untouched (the active modal is the top of the stack) and adds a stack of *suspended* parent frames: new engine seams on `InteractsWithActions` (`suspendCurrentAction` / `resumeSuspendedAction` / `suspendedActionCount` / `getSuspendedActionModals` + `suspendActiveActionIfOpen()`, with a resume-aware `closeMountedAction()`), so **the form `statePath` / validation / binding layer is unchanged**. The standalone host stores suspended frames in `public array $suspendedActions` with records reduced to serializable `{class, key}` descriptors (re-resolved by key, since Livewire does not reliably serialize Eloquent models nested in arrays); the table host stores them under `modal.suspended` in the `StateContainer` (record re-resolved from `recordKey` via the query) and seeds it in `TableStateSchema::defaults`. Rendering draws each suspended parent as a dimmed, inert shell (`wire-core::modals.suspended`, `pointer-events-none`) behind the active modal, and the new `:z-index` prop on the `Modal` / `SlideOver` / `Confirmation` components layers each level by depth (`50 + depth*10`); only the top modal binds `Escape`/click-away. Covered by new `ModalStackingTest` suites (standalone forms host + table host: stack push, parent resume on close, per-level form-data preservation, suspended-modal exposure, footer-action-keeps-nested-open) and `ModalComponentRenderTest` cases (the `z-index` prop and the suspended-shell partial), with the full four-package suite green; verified in a real browser via a new `table-modal-nested` preview + `workbench/scripts/verify-nested-modal.mjs` CDP driver (nested modal on top, dimmed parent behind at the correct z-index, `Escape` pops only the top, parent form value preserved across the round-trip). Documented in [`docs/core/actions.md`](docs/core/actions.md) → "Stacked (Nested) Modals" (EN + CS) and the wire-boost guidelines.

## [1.10.0]

### Added
- **User-level browser-testing selectors + render-loop optimization for the table.** **Every** active part of the table now carries a stable `data-testid` (with an accessible name/role where the control is icon-only), so [Pest v4 Browser Testing](https://pestphp.com/docs/browser-testing) can target it at the user level instead of via brittle CSS — the search box, table-filters trigger + reset + active-filter chips, column picker, page-size selector, pagination (prev/next/numbered), sortable headers, per-column filter cells, body cells (+ `data-column`), inline-edit cells, rows (+ `data-row-key`, plus the mobile `table-card`), select-all / per-row / per-card checkboxes (`role="checkbox"` + `aria-label`), sub-row expanders (`aria-expanded`), the bulk bar + deselect, and **every** action surface: `action-{name}` (row), `header-action-{name}`, `bulk-action-{name}` and `menu-action-{name}` (context-menu / action-group items), all with `aria-label` (the core `Action` button, the table action view, the header/bulk action views and the dropdown-item view were all tagged, so form/standalone actions get it too). Actions and filter options stay reachable by visible text. Alongside this, the render hot loop was optimized: the column-static getters (`getAlignmentClass`, `getResponsiveClasses`, `shouldWrap`, `isEditable`, `hasResponsiveDisplay`) are now resolved **once per column** into a `$columnMeta` map reused by the header and every body cell, instead of being re-called for every cell (N rows × M columns → M). **The same convention was then rolled out across the whole shared UI** (audited in three parallel passes), so an end-to-end flow is mappable, not just the table: every wire-forms field gets a `form-field-{statePath}` container (+ `data-field`) plus per-type control hooks (`form-toggle-{path}`, `form-repeater-{path}-add|remove-{i}`, `form-file-{path}-remove-{i}`, `form-checklist-{path}-select-all`, `form-tags-{path}-remove-{i}`, `form-keyvalue-{path}-add`, `form-datetime-{path}-trigger`, `form-button-{path}`, field/hint actions); the canonical searchable combobox (forms Select + table filters) gets `select-trigger` / `select-search` / `select-option-{value}` / `select-clear`; modal chrome gets `modal-close` / `slide-over-close` / `modal-cancel` / `modal-submit` / `modal-back` / `modal-next` / `confirmation-confirm` / `confirmation-cancel` / `modal-footer-action-{name}`; layout gets `wizard-step-{i}` / `wizard-back` / `wizard-next` / `tab-{i}` / `section-toggle` / `callout-dismiss`; toasts get `toast-dismiss` / `toast-action-{i}` / `toast-expand`; infolist actions get `infolist-action-{name}`; and the sortable drag handle gets `sortable-handle` (`role="button"` + `aria-label`). The rollout goes all the way down to the **granular micro-controls**, following the convention `form-{type}-{statePath}` with sub-controls appending `-{action|value|index}`: the date-time picker's month nav / calendar days / hour-minute-second steppers / clear / done (`form-datetime-{path}-…`), colour-picker swatches (`form-color-{path}-swatch-{color}`), rating stars (`form-rating-{path}-star-{n}`), OTP digit boxes (`form-otp-{path}-{i}`), individual radio / checkbox / checkbox-list options (`form-radio-{path}-{value}`, `form-checkbox-{path}`, `form-checklist-{path}-{value}`), sliders (`form-slider-{path}`), and the markdown/rich/tiptap editor toolbar buttons + tabs + body (`form-editor-{path}-…`) — each carries a `data-testid` (dynamic ones bound per value/index) so even a single star or calendar day is addressable. The full selector reference (all surfaces + the naming convention) is tabulated in the docs. Covered by a `TableTestHooksTest` and a new `FormTestHooksTest` (asserting field containers, per-type controls AND the micro-controls render), with all four package suites (core/forms/table/sortable) green, plus a real-browser check that every hook is queryable in the live previews; documented in [`docs/table/advanced.md`](docs/table/advanced.md) → "Browser Testing Selectors" (EN + CS) with a ready Pest Browser example.
- **Multi-select column filter — `Column::filterAsMultiSelect()`.** Per-column header filters covered text, single-select, date, date-range, number-range and boolean, but there was no way to filter a column by **several** values at once — even though `applyFilterCondition()` already did a `whereIn` for array values, no API or UI exposed it. `filterAsMultiSelect(array|string $options, ?string $placeholder)` adds it, matching **any** of the chosen values (`whereIn`); an empty selection constrains nothing. Options accept an array or an enum class (shared `EnumResolver`). Because Livewire only treats header checkboxes as an array group when the bound value is already an array, `mountWithTable()` now **seeds each multi-select column filter's `columnFilters.<name>` state to `[]`** — without which the second pick would replace the first instead of adding (a bug caught only in the browser). Covered by new `ColumnFilterCoverageTest` cases (config, `whereIn` apply + empty-selection skip, checkbox render) and a `WithTableMultiSelectFilterTest` (mount seeds `[]`, `whereIn` row filtering, empty = all rows), plus a real-browser CDP run (open the dropdown, tick two roles → table narrows via `whereIn` with the panel staying open across the live roundtrip, count in the trigger, clearing restores all rows); a live demo lives at `/previews/table-column-filters`, documented in [`docs/table/columns/editing.md`](docs/table/columns/editing.md) (EN + CS). Both `filterAsSelect` and `filterAsMultiSelect` now render the **canonical searchable combobox** (`wire-core::partials.searchable-select`, the same owner used by the wire-forms `Select` and the table `SelectFilter`) rather than a native `<select>` / bespoke dropdown, so a column select filter gains an in-panel **search** for free (on by default; `Column::filterSearchable(false)` opts out) and looks identical to a form Select. The rest of the header-filter controls (text, boolean, date, number-range) were unified onto one canonical style owner — **`Support\FilterControl::classes()`** — that mirrors the **wire-forms field look** (same border, shadow, background, text size, hover and focus ring as `TextInput`), so the whole filter row reads like the rest of the form UI instead of a mix of native and custom widgets. (Multi-select column filters seed their `columnFilters.<name>` state to `[]` on mount so the combobox's array entangle binds cleanly.)
- **Right-click row context menu — `Table::rowContextMenu([...actions])`.** Power users can now right-click a row to open a menu of actions pinned at the cursor, a shortcut alongside the actions column. The menu's actions are declared **separately** from `->actions()` — an explicit dedicated list, not an implicit mirror of the row toolbar (pass the same objects to match) — and render through the exact menu-item markup of the action-group dropdown (`Action::renderForDropdown()`), so only **visible/authorized** actions appear, action groups are flattened in, and a row with no visible action renders no menu. A new canonical **`wireContextMenu`** Alpine factory (shipped in the pre-built `wire-core-dropdown.js` bundle, loaded via the existing `@assets` floating-assets `<script src>`) pins a teleported `position: fixed` panel at the pointer and clamps it inside the viewport; a module-level guard keeps **only one menu open at a time** (right-clicking another row closes the previous); it closes on outside-click, `Escape`, scroll, or after choosing an action (which runs normally, e.g. opening its modal). The per-row `<template x-teleport>` is a valid script-supporting child of `<tr>`, so no markup is duplicated. Desktop pointer feature (touch devices have no context menu — the actions column remains). Covered by a new `RowContextMenuTest` (dedicated-actions gating, separation from the toolbar actions, menu-HTML incl. hidden-action omission, action-group flattening, empty-when-unconfigured, and render wiring on/off) plus a `DropdownAssetTest` bundle-registration assertion and a real-browser CDP run (right-click opens the dedicated actions at the cursor, single-open across rows, viewport-clamped, choosing/Escape closes, no JS errors); documented in [`docs/table/advanced.md`](docs/table/advanced.md) (EN + CS).
- **Per-user column layout memory — `Table::rememberColumns()`, driver-based.** Toggling columns previously lived only for the component's lifetime (a full page reload reset the layout), so a user's chosen columns never stuck. `Table::rememberColumns('key')` now loads the current user's saved hidden-column set on mount and persists it on every toggle, scoped to `auth()->user()` — **one key serves every user**, so it scales to any number of tables (distinct keys) and users. Where it is stored is a pluggable **`TablePreferenceDriver`** selected in `config('wire-table.preferences')`: `null` (the default — no persistence), `session` (no migration), or `database` (a `table_preferences` row per user+table; publish `--tag="wire-table::migrations"` and migrate — the migration is publish-only, never auto-run). A `TablePreferenceManager` resolves the driver (per-table `Table::preferenceDriver()` override > global default, with a separate `guest` driver so a DB-backed default still falls back to per-session memory for visitors); a stored column that no longer exists is dropped on load, and a "Reset columns" control in the picker clears the saved layout (`resetColumns()`). Covered by a new `TablePreferencesTest` (18 cases: fluent API, manager resolution incl. guest/override/swap/unknown-alias fallback, all three drivers' load/save/forget + scoping, mount-load over defaults, stale-column pruning, toggle-persist, reset-forget, a fresh-mount round-trip, and the reset control's render gating), plus a real-browser CDP check of the toggle persisting across a page reload and the reset restoring defaults; documented in [`docs/table/advanced.md`](docs/table/advanced.md) (EN + CS).
- **Conditional whole-row coloring — `Table::rowColor()` and a Closure-aware `Table::rowClass()`.** Painting a row by a per-record condition previously meant hand-writing background utilities in a `rowClass()` Closure — except `rowClass()` only accepted a static `string` and `getRowClass()` never invoked a Closure, so the documented dynamic-class example did not actually work. `Table::rowColor(string|Closure|null)` now tints an entire row with a semantic role or raw Tailwind hue (`danger`, `warning`, `success`, `primary`, `gray`, … or any hue), resolved through a new canonical **`HasColor::getRowTintClasses()`** owner — the lightest `-50`/translucent-dark tint with a matching same-hue hover, so a tinted row reads cleanly and drops the neutral hover + zebra striping it would clash with (return `null` from the Closure for no tint). `Table::rowClass(string|Closure|null)` was widened so its Closure actually resolves per record (the record is passed in), for arbitrary utilities (font weight, ring, opacity) layered on top of a tint. Both compose into one `Table::getRowClasses($record, $rowIndex)` consumed by the row view, keeping the Blade free of layered conditionals. Covered by new `TableTest` cases (static + Closure resolution, empty-string = no tint, tint suppresses hover/striping, tint + custom class, unknown-color gray fallback) and `HasColorTest` (row tint across the full palette), plus a real-browser CDP check of the rendered tints; a live demo lives at `/previews/table-row-color`, documented in [`docs/table/overview.md`](docs/table/overview.md) (EN + CS).
- **`BarChartWidget::verticalLabels()` — rotate each bar's label vertically beside it.** Long category labels (e.g. package names) truncated or overflowed under/above the bars. `verticalLabels()` moves each bar's label out of the header/caption to a rotated caption (reading bottom-to-top) beside its bar, so long names fit; the value/percentage stays in place. Opt-in and vertical-charts only (finance + system); the horizontal layout is unchanged. Covered by `BarChartWidgetTest` (default off / toggle + rotated render on both vertical variants + horizontal-by-default); documented in [`docs/core/widgets.md`](docs/core/widgets.md) (EN + CS).
- **Named repeater items — `Repeater::itemLabel()`.** Repeater item blocks were headed only by their number (`#1`, `#2`), which makes a collapsed list of items hard to tell apart. `itemLabel(string|Closure|null)` shows a name next to the number, either static or derived from the item's state via a closure (`fn(array $state, int $index): ?string`) — e.g. `->itemLabel(fn ($state) => $state['name'] ?? null)` renders "#1 Ada". The label re-renders on the item's reactive cycle, so pairing it with a `->live()` field updates it as the user types. Covered by `RepeaterTest` (static/closure/null resolution) and a `RepeaterReactivityTest` render case; documented in [`docs/forms/fields/repeater.md`](docs/forms/fields/repeater.md) (EN + CS).
- **`FileUpload` now actually stores uploads — orphan-free, on submit — and merges them with existing files.** Uploads previously never reached the server: the field only client-previewed the picked `File` via Alpine, and no host composed Livewire's file-upload machinery, so nothing was ever persisted. `InteractsWithFileUploads` now composes `Livewire\WithFileUploads` (so `wire:model` file inputs upload for real) and, via the `updated`/`updating` lifecycle hooks, folds each finished upload into the field state as a **pending** `TemporaryUploadedFile` — a **multiple** field appends to whatever was already there (existing paths + earlier pending uploads, captured in `updating`), a **single** field keeps the newest. Files are moved to permanent storage only on **save**: a new `SaveHandler` step walks the schema, and for each `FileUpload` calls `FileUpload::storeUploadedFile()` (honouring `disk()`/`directory()`/`visibility()`/`preserveFilenames()`), dehydrating a single field to one path and a multiple field to an array while keeping already-stored paths — so an abandoned form leaves nothing behind (the temporary upload expires on its own). The field is resolved from the changed state path via `Form::findComponentByStatePath()`, so it works in standalone form hosts and table/form action modals alike; the Blade view renders both stored paths and pending uploads (image previews via disk URL / `temporaryUrl()`, a "Pending upload" label, and index-based removal). Covered by `FieldTypesTest` (`storeUploadedFile` + `preserveFilenames`), `WithFormsTraitTest` (merge stays pending; index removal), and `SaveHandlerTest` (single store, multiple merge, no-upload → null) with `Storage::fake`, plus a real-browser CDP upload round-trip.
  - **`FileUpload` now displays already-stored files, with a per-file remove control.** The field's Alpine view only tracked freshly-selected `File` objects, so editing a record that already had a stored path (or an array of paths) showed *nothing* — the existing upload was invisible and un-removable. `FileUpload::getStoredFiles($state)` now turns the bound state into displayable descriptors (`path`/`url`/`name`/`isImage`), skipping transient `TemporaryUploadedFile` instances and empties and resolving each path to a URL through the configured `disk()` (a value that is already a full URL passes through) — reusing the `ImageColumn` resolution pattern. The Blade view renders those existing files below the drop zone (thumbnail for images, document icon otherwise, a link, and an `×`), separate from the client-side preview of new uploads. Removal is backed by a new canonical host trait **`InteractsWithFileUploads::removeUploadedFile($statePath, $path)`** — composed into every form host (`WithForms`, form/table action modals via `WithActions`/`WithTable`), mirroring `InteractsWithRepeaters` and writing through `StateContainer::writeInto()` so it works inside table action modals too — which drops the path from form state (the physical file is left untouched); `->deletable(false)` renders stored files read-only. Covered by new `FieldTypesTest` cases (deletable toggle, array/single/skip/full-URL descriptors) and `WithFormsTraitTest` host cases (remove from a multiple field, clear a single string path, ignore an absent path), plus a real-browser CDP check of the render + remove round-trip; documented in [`docs/forms/fields/file-upload.md`](docs/forms/fields/file-upload.md) (EN + CS).
  - **Toast notifications gained a countdown bar, action buttons, persistence, a collapsible stack, and a max-visible cap.** `<x-wire-notifications::toast-container />` now renders a per-toast **countdown bar** that depletes toward auto-dismiss and **pauses (with the timer) on hover** — driven by a single `requestAnimationFrame` loop rather than per-toast `setTimeout`s. New container props: `progress` (bar on/off, default on), `stack` (collapse toasts into a pile that fans out on hover; direction from `topAnchored()`), and `max` (cap visible toasts, overflow into a clickable "+N more" pill). The container is now an `aria-live="polite"` region (error toasts `role="alert"`) and honors `prefers-reduced-motion` (no collapse/fan-out, transitions off). `Notification` gained `->persistent()` (sticky: `duration 0`, no bar) and `->action('Undo', 'event')` / `->action(NotificationAction::make(...))` / `->actions([...])`; the new immutable **`NotificationAction`** value object (`Notifications\NotificationAction`: `make(label, event)`, `->payload()`, `->color()`, `->keepOpen()`) renders a toast button that runs `Livewire.dispatch(event, payload)` on click, which the host listens for with `#[On(event)]`. Covered by new `NotificationTest`/`CurrentComponentDriverTest` cases and a real-browser CDP check; a live demo lives at `/previews/core-toasts`, documented in [`docs/core/notifications.md`](docs/core/notifications.md) (EN + CS).

### Fixed
- **Editable `ToggleColumn`/`SelectColumn` cells now update optimistically, and a per-record disabled cell can no longer be written by a forged request.** `updateTableCell()` calls `skipRender()` so the table is not re-rendered (a DOM morph destroys Alpine cell state), which requires each editable cell to switch its own appearance client-side. `TextInputColumn` did this; `ToggleColumn` was a plain `wire:click` and `SelectColumn` a plain `wire:change`, so a toggle's visual only caught up after a reload/poll and neither participated in optimistic-locking or error rollback. All three inline-editable cells now share one canonical Alpine component — **`wireEditableCell`** (shipped in the pre-built `wire-core-dropdown.js` bundle, loaded via the existing `@assets` floating-assets `<script src>` so it survives Livewire morphs and strict CSP) — which flips the cell optimistically, calls `$wire.updateTableCell(...)` with the row's version, rolls back to the last server-confirmed value on failure, adopts the server's value on an optimistic-lock conflict and surfaces the conflict/error message **inline on the cell itself** (a red state on toggle/select/text — no toast or `NotificationManager` setup required; opt in to *also* raise a toast for conflicts with `Table::notifyEditConflicts()`), and reconciles via a `MutationObserver` on `data-server-value`/`data-record-version` when polling refreshes the row. `TextInputColumn`'s editable cell was migrated onto the same base (its live validation / save-on-blur/enter / escape-to-revert now layer on top). **Security:** `ToggleColumn` and `SelectColumn` gained a server-side `canEdit(Model $record)` guard (consulted by `updateTableCell`) so a per-record `disabled()` cell is rejected on the server, not just hidden client-side — record identity is passed via `data-*` attributes rather than interpolated into JS. Covered by a new `WithTableInteractionsTest` case (forged edit to a disabled toggle/select is rejected and does not write; an enabled record still saves), an updated `ColumnPartialRenderTest`, a `DropdownAssetTest` bundle-registration assertion, and a real-browser CDP run (optimistic flip before the server responds, save confirmation, conflict rollback, no JS errors).

### Changed

### Added

## [1.9.0]

### Added
- **Optimistic locking for forms — `Form::optimisticLock()`.** Concurrent edits could silently overwrite each other: two users open the same record, both save, and the second save clobbers the first with no warning — the worst class of data loss in ERP/MES workflows. `Form::optimisticLock(string $column = 'updated_at')` opts a form into a version check: the lock column's raw value is captured when the form is filled from the record and carried through the Livewire round trip, and on save the **authoritative current database value is re-read**; if it no longer matches the captured baseline (someone else saved — or deleted — the record in the meantime) the save is aborted with a `WireForms\Forms\Runtime\StaleModelException` plus a conflict notification (`wire-forms::messages.stale`) instead of overwriting the newer data. Works with a timestamp or any integer/version column; opt-in and fully backwards compatible (no lock unless called). The guard runs only in update mode and fails open when no baseline was captured (e.g. `->model()` set after `->fill()` — set the model first). Covered by `OptimisticLockTest` (happy path, concurrent-change conflict, opt-in control, custom version column, fail-open, bound/unbound conflict notification).
- **Per-record cell visibility — `Column::visibleForRecord()`.** Column visibility (`->hidden()` / `->visible()` / `->authorize()` / `->permission()`) is *structural* — evaluated once, without a record, deciding whether the column exists in the table at all (it also drives the header, column toggle and export, and is memoized once per parent for sub-rows). To hide or **redact a single cell per row** — e.g. show `salary`/`margin` only on records the user may see — the base `Column` gains `->visibleForRecord(fn ($record) => bool)`, consulted at cell render *alongside* the structural check: a denied cell renders empty while the column keeps its place in every other row. It is deliberately a separate closure rather than folded into `canView()`/`authorizeUsing()`, which would misfire structurally with a null record. Wired across the whole column family (text, badge, boolean, icon, image, poll, select, toggle, text-input, split incl. its child columns, and stacked — which also gained the structural `canView()` guard it was missing). `ButtonColumn::visibleWhen()` becomes a backwards-compatible alias for it (one canonical owner). Covered by `ColumnVisibleForRecordTest`; documented in [`docs/table/columns/index.md`](docs/table/columns/index.md).

### Fixed
- **A remotely-searched combobox selection keeps its label after being picked.** In remote-search mode (`Select::getSearchResultsUsing()` / `BelongsToSelect`), choosing an option went blank: the shared `wire-core::partials.searchable-select` reset `search` to `''` on select, which fired the `search` watcher → `fetchRemote('')` → the server returned nothing for the empty term, so `options` was rebuilt from `initialOptions` alone. Because the just-chosen option existed only in the transient remote results (and Alpine never re-reads the render-time `x-data` seed across a Livewire morph — the same constraint behind `upsertOption`), `selectedLabel`/`isSelected`, which read purely from `options`, lost the choice and the trigger fell back to the placeholder — most visibly for a value picked in a fresh create/action modal (an existing record's label survives because the view seeds it via `getSelectedOptionLabels()`). `select()` now persists the chosen option into `initialOptions` **before** resetting the search (new `persistSelectedOption()` helper, mirroring `upsertOption` and the server-side seed), in both the single branch and when a value is *added* in the multiple branch — so the label survives the post-select `fetchRemote('')` and every subsequent remote search. One canonical owner, so the base `Select`, `BelongsToSelect` and the table `SelectFilter` all inherit the fix; non-remote selects are unaffected (no `search` watcher, `options` is never rebuilt). Covered by `SelectTest` (helper present, writes into `initialOptions`, and runs before the search reset in both branches).

### Changed
- **`authorizeUsing()` callbacks now receive the row's record.** The shared `Foundation\Concerns\HasAuthorization` custom-authorization callback was passed only the authenticated user, so `->authorizeUsing(fn ($user) => …)` could not gate per record — even though row actions already carry one. `isAuthorized($context)` now forwards the record to the callback: `->authorizeUsing(fn ($user, $record) => $user->id === $record?->owner_id)`, enabling per-record **action** authorization out of the box (approve only your own records, guard a transition only for the owner). Fully backwards compatible — existing one-argument closures keep working (PHP ignores the extra argument), and record-less surfaces (structural column/filter visibility, fields, widgets) pass `null`. Covered by `HasAuthorizationTest` (per-record forwarding + one-arg backward compatibility). This intentionally does **not** turn structural `Column::canView()` per-record; for per-cell redaction use `->visibleForRecord()` above.
- **`Form::using()` + relationship repeaters — documented behavior, regression-tested.** A custom `using()` callback receives the full data array **including relationship `Repeater` arrays** (e.g. a `children` key), which the default persistence path strips before writing the parent — so a naive `Model::create($data)` inside `using()` would try to mass-assign them. The [save lifecycle guide](docs/forms/save-lifecycle.md) now spells this out: assign only the parent's own attributes, return the persisted `Model` and the Step-6 relationship cascade still runs for you, or return a non-`Model` (an id/DTO/command result) and the cascade is skipped so your callback owns persistence entirely. No behavior change — the cascade already ran for any `Model` result; locked by two `SaveHandlerTest` regression tests (`using()`→Model cascades children; `using()`→non-Model skips).

### Fixed

- **`RepeatableEntry` deep-clones its schema per row.** `getRows()` shallow-cloned each child entry, so a nested `RepeatableEntry` (rows within rows) shared its inner schema instances between every row clone — the same clone-sharing pattern that leaked per-item state paths across `Repeater` items in forms. `RepeatableEntry::__clone` now deep-clones the child schema, mirroring `LayoutComponent::__clone`. ## [1.6.1]

### Added
- **Filament-style reactive state accessors in every field closure.** Dynamic field callbacks — `visible()`, `hidden()`, `disabled()`, `afterStateUpdated()` — now receive `$get`, `$set` and `$state` resolved against the **live** Livewire state bag, so a field can react to a sibling's value without reaching for a global `Livewire::current()` + `data_get()` workaround. The mechanism is a new canonical seam: `EvaluatesClosures::evaluate()` merges named accessors into the evaluated Closure when the component implements the new core contract `Foundation\Contracts\HasStateAccessors`, and `WireForms\Concerns\InteractsWithFormState` supplies them for fields. `$get('sibling')` reads another field under the same `statePath`; `$get()` reads the field's own value **live** (reflecting a `$set` made earlier in the same closure), while `$state` is a snapshot taken at call time; `$set('sibling', $value)` writes through the canonical `StateContainer::writeInto()` so it is StateContainer-safe and works identically inside a table action modal. Documented in the new `docs/forms/reactive-fields.md`.
- **`afterStateUpdated()` reactive hook with a single canonical owner.** A field can run a callback right after its bound value changes — `->afterStateUpdated(fn ($state, $old, $get, $set) => …)` — receiving the new value, the previous value, and the reactive accessors (parameters resolved by name, any subset in any order). Registering a callback **auto-enables `live()`** (without a server roundtrip the hook could never fire). The hook is owned in core by the `Foundation\Concerns\HasAfterStateUpdated` concern behind the `Foundation\Contracts\HasStateUpdatedCallback` contract; both form hosts route to it through one place — `WireForms\Concerns\DispatchesStateUpdates` maps the Livewire `updated` dot-path to the matching prepared field and fires its callback, so standalone `WithForms` components and table action modals share the lookup instead of each re-implementing it.
- **Modal footer actions.** Add extra buttons to an action modal's footer with `->modalFooterActions([ModalFooterAction::make('generate_slug')->action(fn ($data, $set) => …)])`. Each callback receives the live form-data bag as `$data`, a `$set` writer for it, `$component`, and the modal's `$record` / `$records` context, so a footer button can read and write the in-progress form without submitting it. `->submitsForm()` validates the form first, `->closesModal()` closes the modal after the callback returns, and `->position('before'|'after')` places the button around the built-in Cancel/Submit. Owned by `Core\Actions\ModalFooterAction` and the `Modals\Concerns\HasFooterActions` trait, rendered through `tables/partials/modal-footer-actions.blade.php`.

Combined with the accessors above, the `Livewire::current()` workaround is no longer needed.
- **`required()` on a hidden field no longer blocks submit.** `FormValidationResolver` flattened the schema and collected rules from **every** field regardless of `visible()`, so a `required()` rule on a field hidden by `->visible(fn ($get) => …)` failed validation against a value the user could never enter — the form refused to submit and `->action()` never ran. The resolver now skips components whose `isVisible()` is `false` when building rules, messages and attributes (visibility evaluated against live state, so a field toggled hidden by a sibling's value is excluded only while it stays hidden); repeaters are filtered the same way.
- **Multi-step wizard steps for a header action receive runtime context.** `getStepFormInstance($livewire, $context, $step)` passes `$context` into `ModalStep::getSchema($context)`, but for a `HeaderAction` the context was always `null` (header actions carry no record), so a `->schema(fn ($data) => …)` Closure that builds a later step from earlier answers could not resolve. `resolveCurrentModalAction()` and `resolveActionModalFormInstance()` now expose the live `modal.action.formData` bag as the header-action context, so a wizard's second step can branch on what was entered in the first. Covered by `WithTableWizardTest` ("passes the live form-data bag as context to a header wizard step", "builds the second step schema from first-step data").
- **Repeater add / remove / reorder no longer fatals with "Public method [addRepeaterItem] not found on component".** The Livewire action endpoints backing a `Repeater`'s buttons were not exposed on every host that can embed a form. They are now owned by one canonical trait, `WireForms\Concerns\InteractsWithRepeaters` (`addRepeaterItem` / `removeRepeaterItem` / `reorderRepeaterItems`), `use`d by both `WithForms` and `WithTable`, with writes routed through `StateContainer::writeInto()` so they work through the table's `tableState` StateContainer bag as well as plain array properties.

### Changed
- **`StateContainer::writeInto()` is the one writer for nested state.** Writing a value at a dot-path that crosses a `StateContainer` (the bag a table action modal binds) cannot go through `data_set()` — it silently drops the write on the overloaded `ArrayAccess` element. `writeInto()` walks the path, delegates to the container's `set()` / `replace()` when one sits on the path, and falls through to `data_set()` for plain hosts. `StateManager::set()`/`fill()`/`setState()`, the field `$set` accessor, and the repeater mutation endpoints all delegate to it, so the StateContainer-aware traversal lives in exactly one place.

## [1.5.0]

### Added
- **Enum-sourced options auto-add an `in:` validation rule.** When a single-value `Select` or `Radio` takes its options from an enum class, the field is automatically constrained to those keys (`Rule::in([...])`) — a tampered or stale submission outside the enum is rejected without the owner restating the rule. The logic lives on `WireForms\Concerns\HasOptions` behind the new `WireForms\Contracts\ProvidesImplicitValidationRules`, and `HasFormValidation` merges it in. It is skipped when options are a plain array (the set may be dynamic), for multi-value fields (array state can't be a single `in:`), and when the owner already declared an `in:` / `Rule::in()` / `Rule::enum()` rule.
- **`TextInput::datalist()` accepts an enum class.** Passing an enum class uses its case labels as the input's suggestion list, mirroring the option-field shorthand.
- **Enum classes can populate field options directly (Filament-style).** Any option-based surface now accepts a backed/unit enum class-string instead of a `[value => label]` array — `->options(Status::class)` — and expands it to a map keyed by the backing value (or case name for unit enums). Enums implementing `Foundation\Contracts\Enum\HasLabel` render `getLabel()` as the option label; enums exposing a `label()` method use that; everything else falls back to a headline of the case name. The expansion is owned by a single canonical method, `EnumResolver::options()` (plus `isEnumClass()` and the pass-through `normalizeOptions()`), and every surface delegates to it: form `Select`, `Radio`, and `CheckboxList` (via the new shared `WireForms\Concerns\HasOptions` trait), table `SelectColumn`, and table `SelectFilter` (whose former package-local enum `match` map is removed in favour of the shared owner). The generic column-level APIs accept it too — `Column::editable(type: 'select', options: Status::class)`, `Column::filterable(type: 'select', options: Status::class)`, and `Column::filterAsSelect(Status::class)`. Closures returning an enum class are expanded too; arrays pass through untouched.

### Changed
- **A label-less enum now displays a headline of its case name everywhere, not its backing value.** `EnumResolver::label()` (and therefore every display surface — table columns, infolist entries, exports, grouping, filter chips) previously fell back to the raw scalar for an enum that does not implement `Enum\HasLabel` (`Status::Active = 'active'` rendered `active`). It now resolves through the same canonical order as option labels — `HasLabel::getLabel()`, then a `label()` method, then `Str::headline($case->name)` (`Active`, `InReview` → `In Review`) — so the same enum reads identically on a cell, an export, and a `<select>` option. Enums implementing `HasLabel` and non-enum values are unaffected; `scalar()` (used for keys, copy values, comparisons, serialization) still returns the backing value.

### Fixed
- **`Action::visible(Closure)` is honoured again.** The Actions `HasVisibility` trait implemented `visible()` as `hidden(! $visible)`; for a closure, `! $closure` coerced the object to `true`, so the callback was discarded and `hidden(false)` made the action **always visible** — silently bypassing per-record visibility logic such as `->visible(fn ($record) => $record->canEdit())`. The trait now branches on the closure and stores a negating wrapper, matching the Foundation `HasVisibility` behaviour.
- **Repeater state path keeps its form prefix.** A `Repeater` nested in a form (or any layout) never had its own state path set during `prepareChildren()`, so `getStatePath()` dropped the prefix (returned `contacts` instead of `data.contacts`) and the add/remove handlers and `wire:model` bindings wrote to the wrong location. `LayoutComponent` now records a resolved absolute path during preparation (idempotent — re-running never double-applies the prefix) and `Repeater::getStatePath()` reads it.
- **Repeater items are validated at the correct paths.** Repeater child fields were flattened and validated at the template path (`data.label`) instead of the per-item path, so per-item rules never matched real data, and the repeater's own `min/max-items` / `array` rules were never collected (the resolver called `getValidationRules()` while `Repeater` defined `getRules()`). The validation resolver now treats repeaters as opaque during flattening and emits container rules at the repeater path plus per-item **wildcard** rules (`data.contacts.*.label`); `required()` on a repeater adds `required` + `array`.
- **`<x-wire-actions::button>` no longer fatals for header/bulk actions.** The component's fallback (taken when an action has no `getRenderData()`, i.e. `HeaderAction` / `BulkAction`) called the `protected` `resolveSolidColorClasses()` / `resolveButtonSizeClasses()` with missing arguments, throwing `ArgumentCountError`. The fallback now uses a single public `BaseAction::getButtonClasses()` that assembles base + size + color via the canonical resolver.
- **Relation (dotted) filter names work from the UI.** A filter named `customer.status` is bound nested by `wire:model` (`filters.customer.status.value`) but was read back with a flat key, so the value never applied and the chip's remove button couldn't find it. Filter init, the query service, indicator chips, sub-row filters, and `removeTableFilter()` now read/write through `data_get` / `Arr::set` / `Arr::forget` (pruning empty parent nests), so dotted names round-trip end to end.
- **Multi-value field state is typed as an array.** `Select` (multiple) and `CheckboxList` inherited `getStateType() === 'string'`, so a stray scalar was left as a string the bound control couldn't use. Both now report `'array'` (Select only when `->multiple()`), matching `Tags` / `KeyValue` / `FileUpload`.
- **`DateTimePicker` stores a serializable date string, not a Carbon.** The field hydrated its state to a `Carbon` instance inside the Livewire array, which is fragile to serialize and unparseable by the Alpine/native picker. A new format-qualified hydrator type (`date:<format>`) parses any date-like input and returns a mode-appropriate **string** (`Y-m-d`, `Y-m`, `H:i[:s]`, `Y-m-d\TH:i[:s]`); the core `StateHydrator` owns the generic formatting while the field owns its format.
- **Column text filters ignore non-scalar values.** `applyTextFilter()` built `"%$value%"` without a type guard, so a crafted/stale array column-filter value raised an "Array to string conversion" warning and a garbage `LIKE`. Non-scalar values are now ignored.
- **Cleared range filters no longer count as active.** The toolbar derived active filters with a bare `array_filter($tableFilters)`, so a range filter typed then emptied (`['min' => '', 'max' => '']` — a truthy array) stayed "active", contradicting the (correctly empty) indicator chips. The active check now recurses and rejects all-empty values.
- **`Toggle` colours and icons render.** `onColor` / `offColor` / `onIcon` / `offIcon` were fully wired in PHP but the view hardcoded `bg-primary-600` / `bg-gray-200` and drew no icons. The toggle now resolves its track colours via `getOnColorClasses()` / `getOffColorClasses()` (purge-safe, toggle-specific) and renders the on/off icons.
- **Sortable column reordering supports all columns and non-integer user keys.** Non-sortable column `<th>`s emitted no `data-column`, so they couldn't be drag-reordered and were silently dropped from the saved order; every column header now carries `data-column`. The per-user column-order persistence typed the user id as `?int`, throwing on UUID/ULID auth keys — the model, concern, and migration now accept `int|string` (migration column type configurable via `wire-sortable.user_key_type`: `id` / `uuid` / `ulid`).
- **`SortableTable::alwaysReorderable()` actually enables reordering.** The method was missing on the subclass and fell through to a `Table::macro` writing a different property, so `isReorderable()` stayed `false` and reorder mode never engaged. It is now a real method (implying `reorderable()`), and `getOrderColumn()` reads the `wire-sortable.order_column` config default that was previously ignored.

### Changed
- **Bulk-action buttons delegate to the canonical colour owner.** `actions/bulk-button.blade.php` re-encoded the palette with an inline `match` map whose outlined branch only handled `primary` / `danger` (rendering `success` / `warning` / `info` grey); it now calls `getButtonClasses()`, so every hue and the solid/outlined split come from the shared `HasColor` resolver.

### Added

- **Row grouping with subtotals** – `Table::groupBy('customer')` keeps groups contiguous (group order is prepended to the active sort), renders a header row per group (`groupLabel(string|Closure)`), and adds per-group subtotal rows for every column with a summary (`groupSummaries(false)` to disable); the grand-total footer stays.

The enum owns the per-type semantics (default labels, count formatting, SQL portability, empty-set results). Strings stay accepted and are normalized to the enum; unknown type strings now throw an `InvalidArgumentException` instead of silently rendering an empty footer value.

### Changed
- **Rollup grand totals compute in SQL.** Summarizing a rollup column (`->sums()` + `->summarizeSum()`) previously loaded every filtered parent row into memory and summed floats in PHP; the rollup alias is now aggregated in SQL over a derived table — no row loading, database decimal precision.

### Performance
- **Row selection is client-side — a checkbox click no longer costs a server roundtrip.** Selection state lives in Alpine, entangled (deferred) with `tableState.selection.records`: checkboxes, the select-all header state, row highlight, and the selection bar (count, plural label, deselect) all react instantly without re-rendering the table. The server state syncs with the next request (bulk actions always see the current selection); tables with a summary footer auto-commit selection changes debounced (~350 ms) so selection-scope totals and the scope toggle stay correct. Server methods (`toggleRecordSelection()`, `selectAllRecords()`, …) remain for backwards compatibility.
- **`subRowsLimit()` no longer loads full child sets into memory.** The eager load now fetches only `limit` rows per parent (native per-parent eager-load limit, window function) plus one `loadCount` query for exact "show more" totals; parents flagged show-all still load their full set. Previously every expanded/flattened parent loaded *all* children just so the limit could be applied in memory. On Laravel 10 (no per-parent eager-load limit) the loader transparently falls back to the previous full-load + in-memory limit, so behaviour is identical there.
- **Footer summaries batch into a single SQL query.** Every `query`-scoped summary previously ran its own aggregate query on each Livewire render (a footer with 5 summaries = 5+ queries per interaction). All SQL-native summaries now compute in one aggregate query (plus one for rollup columns over the derived table); sub-row grand totals batch the same way over the child query. Closure summaries, statistical types (median, stddev, …), and `when()`-restricted summaries keep the per-summary fallback with identical results.
- **Package views no longer go through the deprecated magic properties.** `index.blade.php` and the sub-row partials read `$component->tableState` directly (precomputed once per render) instead of `$component->tableFilters` & co., which rebuilt the legacy property map on every access — per row, per column. The map itself is now memoized, so user code on the legacy properties is cheaper too.
- **Row loops reuse the precomputed visible-column set.** Header, filter row, body cells, and sub-row tables no longer re-evaluate `canView()` (which may hit the Gate) and `isColumnVisible()` per cell — visibility resolves once per render (once per parent for sub-rows).
- **Selected records are memoized per request** (selection-scope summaries, grand totals, and bulk modals previously each ran the same query) and **group subtotals partition the page once** instead of re-filtering all page records per group.
- **`StateContainer::get()` traverses the path once** instead of the previous `has()` + `resolve()` double walk — it runs hundreds of times per table render.
- Capability auto-resolution in `TableQueryService` is skipped when the metadata registry holds no column/accessor metadata — removes a no-op per-column walk from every query build.

### Fixed
- **Query cache no longer serves page 1 for every page.** Pagination is applied inside the cache callback, so the page number was missing from the cache key (`cacheQuery()`) — all pages shared one entry for the TTL. The current page (or cursor) is now part of the key, including with a custom `cacheQuery(key: …)`.
- **`subRowsLimit()` on Laravel 10 showed too few children.** The per-parent eager-load limit (a window function) only exists on Laravel 11+; on Laravel 10 it applied a single global `LIMIT` across all parents, so the first parent received fewer than `limit` rows. The loader now detects the framework capability and falls back to full-load + in-memory limiting on Laravel 10.


## [1.1.0]

### Added
- **Sub-row scoped table filters** – `Filter::subRows()` targets the child records of `Table::subRows()`: parents reduce to those with a matching child (`whereHas`), expanded panels show only matching children, and rollup aggregates (`->sums()`, `->counts()`, …) plus their footer grand totals count only the matching children.
- **`DateFilter::month()`** – Month/Year filtering (`whereYear` + `whereMonth`) rendered as a native month picker; combines with `subRows()` for filtering by the month of child records.
- **`DateTimePicker::asMonth()`** (wire-forms) – month mode rendering a native `<input type="month">`.
- **URL query-string persistence** – `Table::queryString()` keeps search, sort, per-page, and filter state in the URL (shareable/bookmarkable table views). Incoming values are validated against the table config; an optional prefix (`queryString('orders_')`) avoids collisions between multiple tables on one page.
- **Filter indicator chips** – active filters render as removable chips under the toolbar with per-type labels (option labels, range bounds, translated month names); customizable via `Filter::indicator(string|Closure)`, removable via the new `removeTableFilter()` action.

### Fixed
- Multiple-select filter (`SelectFilter::multiple()`) no longer crashes the select view when an array value is active, and renders the selected options correctly.
- **Action modal forms no longer lose typed text.** Action forms forced `wire:model.live` on every field, so each keystroke pause triggered a full component re-render whose DOM morph raced further typing and erased it. Fields now default to deferred `wire:model` (values are sent with the submit call), eliminating both the text loss and the per-keystroke server roundtrip + table re-render. Fields that drive reactive behavior opt in per field via `->live()`.
- **Rollup columns export their values.** Exporters resolved cell values only by column name, so a rollup column named differently from its aggregate attribute (e.g. `items_total` vs `items_sum_line_total`) exported empty cells; exporters now read the computed aggregate attribute.

### Migration Guide

1. Update `composer.json`:
   ```bash
   composer require nyoncode/wire-table:^0.1
   ```
   This will automatically install `wire-core` and `wire-forms`.

2. Find and replace namespaces in your codebase using the table above. Most common replacements:
   ```
   NyonCode\WireTable\Actions\ → NyonCode\WireCore\Actions\
   NyonCode\WireTable\Forms\Fields\ → NyonCode\WireForms\Components\
   NyonCode\WireTable\Notifications\ → NyonCode\WireCore\Notifications\
   ```

3. Layout components moved to sub-namespace:
   ```
   NyonCode\WireForms\Components\Layout\Section
   NyonCode\WireForms\Components\Layout\Grid
   NyonCode\WireForms\Components\Layout\Fieldset
   ```

4. Display components moved to sub-namespace:
   ```
   NyonCode\WireForms\Components\Display\Alert
   NyonCode\WireForms\Components\Display\Html
   NyonCode\WireForms\Components\Display\Placeholder
   NyonCode\WireForms\Components\Display\ViewField
   ```

5. DatePicker/TimePicker unified into `DateTimePicker`:
   ```php
   // Before:
   DatePicker::make('birth_date')
   TimePicker::make('start_time')

   // After:
   DateTimePicker::make('birth_date')->asDate()
   DateTimePicker::make('start_time')->asTime()
   ```

6. Blade render syntax changed:
   ```blade
   {{-- Before --}}
   {!! $this->getTable() !!}

   {{-- After --}}
   {{ $this->table }}
   ```

7. If you customized notification driver config, update class references to `NyonCode\WireCore\Notifications\Drivers\*`.
