# V2.3 — Aplikační owner vrstva: implementační plán

Rozpracování fáze **V2.3** z [`v2-master-plan.md`](v2-master-plan.md) podle
[ADR 0020](../decisions/0020-application-owner-layer.md). Cíl: první-třídní
`Resource`/`Page`/`Workspace` vrstva, která **skládá** existující primitivy
(ADR 0017 layer 4, gap #1).

## 0. Stav (ověřeno v kódu 2026-07-06) — greenfield, ale primitivy hotové

**Beze korekce scope** — na rozdíl od V2.1/V2.2 tady nic z owner vrstvy zatím
neexistuje (`Resource`/`ListPage`/`EditPage`/`Workspace`/`Navigation` = 0 v
`packages/*/src`). Zásadní ale je, že **všechny primitivy, které owneři skládají,
už existují a jsou zralé**:

| Primitiv | Stav | Owner ho použije v |
|---|---|---|
| `Table` + `WithTable` | zralé (po V2.1 headless) | `ListPage` |
| `Form` + `WithForms` | zralé | `Create/EditPage` |
| **`Infolist`** (`record()`/`schema()` + Text/Badge/Icon/Image/Boolean/Color/List/Repeatable entries) | **zralé** — read-only view surface hotový | `ViewPage` (řeší ADR 0020 open Q2 → ANO) |
| **`RelationManager`** (`mount(ownerRecord)`, `getTable`, `createRelatedRecord`/`attach`/`detach`) | **zralé** — jediný existující owner = **šablona** | povýšit pod vrstvu |
| `Widget` + `WithWidgets` | zralé | `Dashboard` |
| boost `ComponentScanner::scan()` + `Describe{Form,Table,Infolist}` | zralé | vzor pro registraci + `DescribeResource` |

**Závěr:** V2.3 je aditivní kompozice nad hotovými primitivy. Riziko je
**návrhové** (nerozbít standalone jednoduchost), ne technické.

## 1. Hard-gate: V2.1 PRVNÍ (ADR 0017 explicitní riziko)

Owner vrstva **nesmí** začít před dokončením V2.1 (headless `WithTable`). ADR 0017
to jmenuje jako přímé riziko: *„pokud se nejprve nerozřeže `WithTable`/`Column`,
nová resource/page vrstva se jen nalepí na stávající monolity."* `ListPage`/
`EditPage` musí skládat **headless collaborators + tenký adapter**, ne 3213řádkový
trait. → V2.3 start = V2.1 DONE.

## R — `Resource` + registry (integrační owner)

### R.1 `Resource` kontrakt
Váže entitu (model / `DataSource` z V2.0) a deklaruje její povrchy na jednom místě.

```php
abstract class Resource
{
    public static function model(): string;              // nebo dataSource(): DataSource
    public function table(Table $table): Table;
    public function form(Form $form): Form;
    public function infolist(Infolist $list): Infolist;
    /** @return array<class-string<RelationManager>> */
    public function relationManagers(): array;
    /** @return array<class-string> */  // Page komponenty
    public function pages(): array;
    public function navigation(): NavigationItem;
    public function policies(): void;                    // authorize* wiring
}
```

**Rozhodnutí (ADR 0020 open Q1 — locking): hybrid.** Statická metadata
(`model()`, `navigation()` — potřeba bez instancování pro registry/menu) +
instanční kompozice (`table()`/`form()`/`infolist()` — konzistentní s
`RelationManager`/`WithTable` trait vzorem). Ne čistě static (Filament), ne čistě
instance (Nova).

> **⚠️ Otevřené rozhodnutí — vlastník `ResourceRegistry`. Musí padnout před V2.3.a.**
>
> Frontmatter téhle fáze ukládá `Resource`/`ResourceRegistry` do `packages/table`
> a `Workspace`/`Navigation` do `packages/core`. `Workspace` ale grupuje
> `Resource`y a `v2.5` staví global search v `core/src/GlobalSearch/` nad tímtéž
> registrem — core by tedy muselo vidět na table, zatímco table už závisí na core.
> To je cyklus, a `AI_CHANGE_PROTOCOL.md` ho vede jako Red Flag („the change
> requires modifying `core` to know about `forms`, `table`, or `sortable`").
>
> Rozpad core na balíčky ho nevyřeší — [ADR 0025](../decisions/0025-core-module-layers.md)
> ho zamítl, dokud pro něj není jmenovaný konzument. Řešení je tedy uvnitř
> dnešní topologie: kontrakt `Resource` + `ResourceRegistry` v `core/src/Resources/`
> (vrstva L1 podle ADR 0025), implementace resource typů zůstane v `packages/table`.
> **Rozhodnuto 2026-08-26 (vlastník repa):** kontrakt `Resource` +
> `ResourceRegistry` do `core/src/Core/Resources/` (vrstva L1 podle ADR 0025),
> implementace resource typů zůstane v `packages/table`.
>
> **PŘEHODNOCENO 2026-08-30 — celá owner vrstva jde do `packages/table`.**
> Důvod je, jak to řeší Filament, ověřeno proti jeho docs 5.x: `Resource` tam
> bydlí v **panel balíčku**, který závisí na `filament/tables`, `filament/forms`
> i `filament/schemas` — tedy **nad** komponentami, ne pod nimi. Komponentové
> balíčky o `Resource` nevědí a *"can be used outside of a panel"*. Filament to
> omezení nemá, protože owner vrstvu dal nahoru.
>
> Uložit kontrakt do `core` znamenalo dát ho na **dno** grafu
> `sortable → table → forms → core`, a odtud plynulo to omezení „nesmí jmenovat
> `Table`/`Form`/`Infolist`". Náčrt R.1 níž je jimi psaný, takže **nešel napsat
> tak, jak je napsaný** — buď by musel vzniknout tři nové dvojice
> kontrakt+factory po vzoru `ModalForm`, ještě než existuje první resource.
>
> `packages/table` už na `wire-forms` i `wire-core` závisí, takže tam `Resource`
> smí jmenovat `Table`, `Form` i `Infolist` přímo, žádné nové seamy nevznikají a
> cyklus taky ne (nic na table nezávisí kromě `sortable`). Global search z V2.5
> pak patří tamtéž, ne do `core/src/GlobalSearch/` — to je ta stejná chyba
> obráceně. Alternativa „nový top balíček `wire-panels`" (přesný Filament tvar)
> zůstává otevřená pro chvíli, kdy owner vrstva přeroste table.
>
> Zůstává v platnosti: `Resource` je **interface + `Concerns/`**, ne
> `abstract class` — a měření to zpřísnilo. `AI_CODING_STANDARD.md` § Interfaces
> říká „one interface represents exactly one capability", takže osmimetodový
> `Resource` neprojde ani jako interface. Rozpadlo se to na
> `DescribesResource` (identita) + `ProvidesResourceTable` / `ProvidesResourceForm`
> / `ProvidesResourceInfolist` (povrchy), viz `v2-progress.md` §2.
>
> Omezení, které z toho plyne a je závazné: kontrakt v core **nesmí jmenovat nic
> z L2 ani z downstream balíčků** — tedy ani `Table`/`Form` (cizí balíček), ani
> `Infolist`/`Widget`/`Action`/`Modal` (L2 uvnitř core). Zbývá `Htmlable` a
> `Foundation\Contracts\*`.
>
> Repo ten tvar už jednou vyřešilo: `Actions\Contracts\ModalForm` +
> `ModalFormFactory` je přesně „core potřebuje formulář, ale nesmí jmenovat
> `Form`". Následovat ten precedens, ne vymýšlet nový mechanismus.
>
> Druhá věc, kterou audit našel a která se tím nemění: `Resource` má být
> **interface + `Concerns/`**, ne `abstract class` — `AI_CODING_STANDARD.md`
> abstraktní třídy zakazuje, pokud nesplní všechny podmínky, a osm abstraktních
> metod bez sdíleného stavu je nesplňuje. `ResourceRegistry` patří pod
> `Managers/` vedle `PluginManager`.

### R.2 Registry (lehký, ne Panel Builder)
```php
final class ResourceRegistry
{
    public function register(class-string<Resource> $resource): void;
    /** @return array<class-string<Resource>> */
    public function all(): array;
    public function forModel(string $model): ?Resource;
}
```
- Registrace: **config array** primárně (`config('wire.resources')`), attribute
  discovery volitelně (**ADR 0020 open Q4 — locking: config primární + opt-in
  discovery** přes `ComponentScanner` vzor). Žádný URL shell / panel.

## P — `Page` owneři (Livewire komponenty přes host traity)

Stejný vzor jako `RelationManager` (Livewire `Component` + host trait). **Všechny
standalone-použitelné bez `Resource`** (ADR 0020 invariant: dvě cesty first-class).

| Page | Host trait | Zdroj schématu | Poznámka |
|---|---|---|---|
| `ListPage` | `use WithTable` | `Resource::table()` | mirror `RelationManager` bez owner-scope |
| `CreatePage` | `use WithForms` | `Resource::form()` | persist přes forms runtime (`SaveHandler`) |
| `EditPage` | `use WithForms` | `Resource::form()` + fill z recordu | + embed `relationManagers()` |
| `ViewPage` | (Infolist render) | `Resource::infolist()` | read-only; + embed relation managers |

**Odemčení z V2.0:** `ViewPage`/akce konzumují `RecordContract` (ne `Model`) →
owner funguje i nad non-Eloquent zdrojem. **Non-Eloquent persistence** (ADR 0020
open Q3): Create/Edit přes `Form::using` (write seam už funguje); dedikovaný
`DataSource` write kontrakt je mimo V2.3 (odkaz na V2.0 open Q4).

---

## RM — Povýšit `RelationManager` pod vrstvu

`RelationManager` už je hotový owner — jen ho zařadit: `Resource::relationManagers()`
ho listuje, `EditPage`/`ViewPage` ho embedují (`@livewire(...)` beze změny).
**Žádný BC break** na stávajícím `@livewire(PostsRelationManager::class, [...])`.

---

## W — `Workspace` / `Dashboard` / `Navigation`

- `NavigationItem` (label/icon/group/sort/badge) — value object nad Foundation
  `HasIcon`/`HasLabel` (canonical owner, ne nová mapa).
- `Workspace` — grupuje resources + dashboards + navigaci pro business oblast;
  **seam pro budoucí Domain Module axis** (V2.6) a Panel Builder (V3).
- `Dashboard` — skládá `Widget`y přes `WithWidgets` (už existuje).

## I — Introspekce + docs

- boost `DescribeResource` MCP tool (mirror `DescribeTable`/`DescribeForm`) —
  vypíše resource povrchy/pages/relations. Registrovat do `ListWireComponents`.
- Docs `docs/application/resources.md` + `architecture/` owner sekce; boost
  guidelines (owner vrstva jako doporučená kompozice pro CRUD).

## Roadmap (fázovaná, aditivní)

| Sub-fáze | Obsah | Závislost | Riziko | Odhad |
|---|---|---|---|---|
| **V2.3.a** | `Resource` + `ResourceRegistry` + `ListPage`; povýšit `RelationManager` | **V2.1 DONE** | nízké | 3–4 d |
| **V2.3.b** | `CreatePage`/`EditPage`/`ViewPage` (WithForms + Infolist); cross-surface policy flow; embed relation managers | .a | střední (návrh) | 4–5 d |
| **V2.3.c** | `Workspace`/`Dashboard`/`NavigationItem` + boost `DescribeResource` + docs | .a, .b | nízké | 3 d |

**Celkem ~10–12 dní.** Vše aditivní → **žádné deprecations**, standalone primitivy
i `@livewire(RelationManager)` beze změny.

### Milníky & kritická cesta
```
V2.1 DONE (hard-gate) ──► M1: Resource skládá ListPage z Table (V2.3.a)
                             │  standalone Table beze změny (dvě cesty žijí)
                             ▼
                      M2: Edit/View/Create + relation managers embedded (V2.3.b)
                             │  cross-surface: sloupce/labely/policy/tenant scope z jednoho Resource
                             ▼
                      M3: Workspace/Dashboard/Nav + boost introspekce (V2.3.c) → V2.3 DONE
```
- **M2 = jádro hodnoty** — jeden `Resource` deklaruje entitu a list/edit/view/relace
  jsou konzistentní (single-declaration). Tady se pozná, jestli owner vrstva
  skutečně skládá primitivy, nebo je duplikuje.
- **Kritická cesta = návrhová kvalita `Resource` API** (R.1 hybrid), ne technika.

## Testovací strategie

- **Standalone-parity (primární invariant):** existující standalone `Table`/`Form`/
  `Infolist`/`RelationManager` testy **zelené beze změny** — důkaz, že owner vrstva
  je aditivní, ne přepsání.
- **Owner unit/feature:** `Resource` skládá správné povrchy; `ResourceRegistry`
  register/forModel; každá `Page` mountne a vyrenderuje z `Resource`; cross-surface
  konzistence (stejné sloupce/policy v list i view).
- **PHPStan gotcha:** `Page` komponenty jsou konkrétní `WithTable`/`WithForms`
  hosti → stejný problém jako `RelationManager` (dnes v `excludePaths`). Po V2.1
  headless splitu by měl být `WithTable` analyzovatelný čistěji; jinak Pages
  vyloučit konzistentně (viz `RelationManager` gotcha [[filament_parity]]).
- **Matrix:** `composer test:table` + `test:core` + `test:forms`; `Integration`
  (owner mount, page render, relation embed); `analyse` + `lint`.

## Rizika & mitigace

| Riziko | Mitigace |
|---|---|
| Nalepení na monolit (ADR 0017 riziko) | **hard-gate V2.1 DONE** před startem |
| Rozbití standalone jednoduchosti | standalone-parity testy zelené; dvě cesty first-class, standalone **nedeprecovat** |
| Scope creep do Panel Builderu | registrace lehká (config array); **žádný URL shell/panel** ve V2.3 (V3) |
| Dvě cesty (owner vs standalone) matou docs | docs explicitně: kdy owner, kdy standalone |
| `Resource` API špatně navržené (Q1) | prototyp R.1 na 1 reálné entitě před rozšířením; hybrid static/instance |

## Definition of done

1. `Resource` + `ResourceRegistry` + `ListPage`/`CreatePage`/`EditPage`/`ViewPage`
   + `Workspace`/`Dashboard`/`NavigationItem` existují, plně otestované.
2. `Resource` skládá primitivy (nevlastní jejich internals — ADR 0020 invariant);
   cross-surface konzistence z jedné deklarace.
3. `RelationManager` povýšen pod vrstvu bez BC breaku; embedován v Edit/View.
4. Standalone primitivy + `@livewire(RelationManager)` beze změny (parity testy zelené).
5. boost `DescribeResource` + docs (`docs/application/resources.md`) + guidelines.
6. `analyse`/`lint` čisté; owner Pages konzistentně řešené vůči PHPStan.
7. `v2-master-plan.md` V2.3 exit odškrtnut; ADR 0020 → ACCEPTED; odemyká V2.6
   domain modules a V3 Panel Builder.
